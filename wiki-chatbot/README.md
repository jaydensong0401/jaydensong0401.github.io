# Wiki-ChatBot 포트폴리오 페이지 개편 기획서

개편 기준일: 2026-11-09  
대상 페이지: `/wiki-chatbot/`  
공개 주소: <https://jaydensong0401.github.io/wiki-chatbot/>

## 1. 개편 목적

방문자가 첫 화면에서 실제 서비스의 모습과 이용 목적을 이해하도록 한다. 기존의 ‘이 혜택을 적용할 수 있는가’에 치우친 소개를 확장해, 제네시스 정책을 질문하고 근거와 함께 정리하며 변경 사항을 관리하는 사내 업무 시스템으로 설명한다.

상단에는 사용자 요청에 따라 마스킹하지 않은 실제 서비스 원본 캡처를 배치한다. 엑셀 데이터의 청킹 방식과 그 이유, 화면에서 내부 정책을 추가하는 방법을 보강한다. 본문의 핵심 흐름인 **작업 방식 → 답변 구조 → 운영 방식**은 유지한다. 서비스의 이용자, 다루는 정책, 질문과 답변의 기준, 정책 변경의 책임이 이 순서 안에서 자연스럽게 이어지도록 구성한다.

## 2. 서비스 정의와 사용자

**Wiki-ChatBot은 사내 임직원이 제네시스 전 차종의 혜택 오퍼링·프리빌리지·기프트 정책을 질문하고, 관련 근거를 확인하며 정책을 정리하는 사내 전용 질의응답 및 정책 정리 시스템이다.**

여기서 ‘사내 임직원’은 시스템의 이용자를 뜻한다. ‘임직원 전용 할인 혜택’으로 서비스 범위를 좁혀 설명하지 않는다. 차종·연식·기준일과 정책 유형에 따라 달라지는 정보를 업무 맥락에서 찾아보고 정리하는 것이 핵심이다.

| 사용자 | 필요한 일 | 페이지에서 설명할 경험 |
| --- | --- | --- |
| 사내 임직원 | 혜택 오퍼링·프리빌리지·기프트의 구성과 관련 정책 확인 | 질문 입력, 질문 범위 지정, 답변과 출처 확인, 필요한 답변 저장 |
| 정책을 정리하는 담당자 | 새 자료와 정책 변경 사항 제안 | 자료 등록·수정 제안, 적용 대상과 기간 정리, 검토 상태 확인 |
| 관리자 | 변경 자료의 검토와 답변 반영 관리 | 검토·승인·수정 요청, 적용일 확인, 원본·현재 적용본·변경 이력 확인 |

전 차종은 서비스가 다루는 업무 범위의 정의다. 모든 차종·정책 질문에 대한 답변 정확도나 자료 완전성을 검증했다는 의미로 사용하지 않는다.

## 3. 핵심 메시지와 문구 원칙

첫 화면에서 ‘누가, 무엇을 물어보고, 어떤 방식으로 정리하는 서비스인지’를 함께 전달한다.

- 서비스명: Wiki-ChatBot
- 서비스 분류: 사내 전용 질의응답 · 정책 정리
- 핵심 소개: 제네시스 전 차종의 혜택 오퍼링·프리빌리지·기프트 정책을 사내 임직원이 질문하고, 조건과 근거를 확인하며 정리하는 시스템
- 설명의 중심: 단순한 혜택 적용 가능 여부를 넘어 정책 구성·대상·기간·관련 자료·변경 사항의 확인

‘질문’, ‘답변’, ‘정책 정리’, ‘근거’, ‘적용 조건’을 구체적으로 사용한다. ‘혜택 적용’은 실제 정책의 적용 조건을 설명할 때에만 사용한다. 업무 질문의 예시는 특정 정책의 진위를 주장하지 않는 일반적인 형태로 작성한다. 예를 들어 ‘차종·연식별 프리빌리지 구성을 정리해 줘’와 같이 기능의 사용 목적을 설명한다.

## 4. 페이지 구성

| 순서 | 영역 / 식별자 | 전달할 내용 | 화면과 구성 |
| --- | --- | --- | --- |
| 최상단 | 실제 서비스 화면과 소개 | 실제 화면을 먼저 보여 주고 서비스 정의와 이용자를 명시 | 마스킹 전 원본 답변 화면을 넓게 배치하고 캡처 설명·확대 동작 제공 |
| 01 | 작업 방식 / `#work` | 정책을 질문하고 정리하기까지의 업무 흐름 | 질문 → 범위 확인 → 관련 자료 확인 → 답변·정리 → 저장·후속 확인, 질문 범위 화면, 엑셀 청킹 설명 `#chunking` |
| 02 | 답변 구조 / `#answer` | 답변을 판단할 때 필요한 조건과 근거 | 정책 내용·대상·기간·출처·버전의 관계 |
| 03 | 운영 방식 / `#operations` | 정책 변경과 실제 답변 반영의 책임 | 내부 정책 추가 방법 `#policy-add`, 작성·검토 화면, 자료 제안 → 관리자 검토 → 승인·적용일 확인 → 이후 답변 반영 |
| 04 | 검증 범위 / `#scope` | 구현한 기능과 앞으로 확인할 품질을 구분 | 현재 기능, 독립 업무 질문 평가·운영 검증 과제 |
| 하단 | 과거 참고 자료 / `#gallery` | 기존 기획 기록을 필요할 때 열람 | 2026-10-26 작성한 소개 자료 8장을 닫힌 펼침 영역으로 보관 |

페이지 안의 이동 링크는 `#work`, `#answer`, `#operations`, `#scope`에 연결한다. 세부 설명은 작업 방식 안의 `#chunking`, 운영 방식 안의 `#policy-add`로 찾을 수 있게 한다. 위 세 본문 영역은 작업 방식 → 답변 구조 → 운영 방식 순서로 유지하고, 기존 소개 슬라이드가 이 흐름보다 먼저 나오지 않도록 한다.

### 작업 방식: 질문을 업무 자료의 정리로 연결

사내 임직원이 자연어로 질문하고 필요할 때 차종·연식·기준일을 지정한다. 모호하거나 충돌하는 조건은 추가 확인으로 좁힌다. 관련 자료를 선택하고 연결된 정책을 함께 확인한 뒤, 근거가 있는 답변과 정책 내용을 정리한다. 필요한 답변은 개인 저장 목록과 기존 대화에서 다시 확인할 수 있다.

이 영역은 기능 목록보다 사용자의 실제 행동을 중심으로 설명한다. 정책 자료가 흩어져 있고, 같은 주제도 대상과 시점에 따라 달라져 다시 확인해야 한다는 업무 문제를 연결한다.

### 작업 방식 안의 엑셀 청킹: `#chunking`

엑셀의 내용을 일정한 글자 수로만 나누는 대신, 혜택·조건·옵션·바우처·회차·일정을 고유 ID가 있는 업무 레코드와 필드로 정리한 뒤 검색 자료를 생성한 과정을 설명한다. 같은 이름이라도 고유번호·차종·연식·조건이 다르면 별도 항목으로 유지한다.

| 처리 | 구현한 방식 | 선택한 이유 |
| --- | --- | --- |
| 업무 레코드와 관계 정리 | 서비스·상품·옵션 등을 고유 ID로 구분하고, 고유번호·코드로 관련 항목 연결 | 이름이 같은 다른 정책을 섞지 않고, 혜택과 적용 조건을 함께 확인하기 위해 |
| 필드 단위 텍스트화 | 각 값을 `필드명: 값`으로 표현 | 잘라낸 값이 어떤 의미인지 검색·답변 단계에서도 유지하기 위해 |
| 긴 값 분할 | 긴 필드 값은 1,200자 단위로 나누고 매 조각에 필드명 반복 | 긴 설명을 다룰 수 있는 크기로 나누면서 필드의 맥락을 잃지 않기 위해 |
| 검색 단위 묶기 | 필드 단위를 약 1,700자 기준으로 묶고 공통 문맥·확인사항 추가 | 검색할 내용의 크기와 업무 항목의 문맥을 함께 관리하기 위해 |
| 메타데이터와 부모 연결 | 원본 위치·레코드 ID·부모 ID·차종·연식·기간·환경·검토 상태·관련 ID·이슈 보존 | 찾은 조각에서 상위 서비스와 관련 조건, 출처로 이어질 수 있게 하기 위해 |
| 변경 추적 | 내용과 연결 문맥의 해시로 추가·변경·삭제 및 영향을 받는 자료 식별 | 공통 정책이 바뀔 때 연결된 검색 자료와 부모 문서를 함께 갱신하기 위해 |

1,200과 1,700은 **문자 수 기준**이다. 필드명·공통 문맥·메타데이터·확인사항이 추가되므로 최종 청크의 엄격한 최대 길이를 뜻하지 않는다. 서비스 종속 또는 상품 옵션의 상위 항목이 하나일 때 그 ID를 부모로 연결하며, 연결이 모호한 자료를 임의로 합치지 않는다.

여기서 청킹은 엑셀 원장의 **전처리 설계**다. 현재 답변 검색은 생성한 청크 파일의 벡터 검색이 아니라, DB의 적용 가능한 수정본을 기준으로 코드 일치·BM25·차종/연식/기간 조건·관련 자료 연결을 사용한다. 수입 시에는 항목 자체의 본문과 관계를 보존하며, 부모 문서에 복사된 과거 내용을 현재 정책으로 재사용하지 않는다. 전처리 설명과 현재 검색 경로를 구분해 도식 또는 문구로 제시한다.

### 답변 구조: 내용·조건·근거를 함께 확인

혜택 오퍼링·프리빌리지·기프트의 관련 내용을 정책별로 정리하되 차종·연식·기준일과 적용 기간을 함께 설명한다. 자료가 부족하거나 조건을 확정할 수 없으면 확인이 필요한 부분을 드러낸다.

답변에 사용한 출처와 당시 수정 버전·검토 상태를 연결한다. 저장한 답변도 당시의 답변과 근거를 보존하므로 현재 정책과 과거 답변의 기준을 구분해서 설명한다. 표 형태의 정리는 정보를 비교하고 확인하기 위한 답변 표현의 하나로 소개한다.

### 운영 방식: 제안과 승인, 적용 시점을 구분

신규·수정 자료는 임시 저장과 등록을 거쳐 관리자 검토 대상으로 보낸다. 승인 대기 자료는 현재 답변에 바로 반영하지 않으며, 관리자가 내용·적용 대상·기간을 확인해 승인하거나 수정을 요청한다.

승인과 시행은 서로 다른 조건이다. 미래 시작일의 승인본은 시작일부터 답변 근거로 사용하고, 만료된 자료를 과거 버전으로 자동 대체하지 않는다. 원본·현재 답변 적용본·변경 이력을 구분해 관리한다. 기존 대화의 답변과 근거는 당시 상태로 보존한다.

최초 수입한 미검토 원본은 상태를 안내하며 검색에 사용될 수 있다. 따라서 ‘모든 답변은 승인된 자료만 사용한다’고 설명하지 않는다.

### 운영 방식 안의 내부 정책 추가 방법: `#policy-add`

실제 화면의 버튼 이름과 작성 항목을 사용해, 임직원이 새 정책을 등록하고 관리자가 검토하는 절차를 설명한다. 작성 화면과 검토 화면을 함께 배치한다.

1. 로그인 후 상단 **정책 추가**를 눌러 오른쪽 작성 패널을 연다.
2. 필수 항목인 **제목·내용**을 입력하고, 적용 차종·연식·시행일·종료일을 확인한다. 차종과 연식을 비워 두면 전체 범위로 처리되므로 의도한 대상인지 확인한다.
3. 필요하면 **수정한 파일에서 내용 가져오기**로 UTF-8 `.md` 또는 `.txt`를 가져온다. 파일은 200KB 이하, 본문은 50,000자 이하이며, 파일을 읽으면 작성 중인 본문이 파일 내용으로 바뀐다. 제목·차종·기간·본문을 등록 전에 확인한다. 정책 추가 화면의 파일 가져오기를 엑셀 직접 업로드로 설명하지 않는다.
4. **임시 저장**은 작성 중인 `draft`로 남기며 답변에는 반영하지 않는다. **정보 등록하기**는 `pending` 승인 대기로 보내 관리자 검토를 요청한다.
5. 관리자는 **정책 관리**에서 내용·적용 범위·근거·기간을 확인하고 **승인하고 반영 → 관리자 승인 확정**, 또는 사유를 적어 **수정 요청**을 진행한다.
6. 승인 후에는 적용일과 질문 범위에 맞는 새 답변에 사용한다. 미래 시행일은 해당 날짜부터 적용하며, 기존 대화의 답변과 당시 근거는 보존한다.

날짜의 **알 수 없음** 상태는 임시 저장·정보 등록이 가능하지만, 관리자가 날짜를 확인하기 전에는 승인·답변 반영이 차단된다. 기존 자료의 수정본은 내용과 적용 범위 전체를 교체하므로, 서로 다른 차종의 내용을 함께 유지해야 할 때는 별도 정책으로 추가한다.

사용할 파일은 2026-10-21에 촬영한 실제 PC 화면의 **마스킹 전 원본 캡처**이며 모두 1440×1000이다. 이번 작업에서 새로 촬영한 화면으로 표현하지 않는다. 사용자의 마스킹 제거 요청에 따라 기존 원본을 적용하고, 예시 데이터 데모나 새 시안으로 설명하지 않는다.

화면에 보이는 기존 정책과 계정 정보는 원본 이미지 그대로 사용한다. 화면 안의 비공개 내용을 별도로 추출하거나 정책 원문·계정·사내 주소를 페이지 본문과 기획서에 새로 인용하지 않는다. 종전의 ‘민감정보 가림 처리’ 캡션·대체 텍스트·설명은 원본 사용 사실에 맞게 수정한다.

캡처에는 무엇을 보여 주는지 설명하는 대체 텍스트와 캡션을 제공한다. 상단 이미지는 바로 불러오고, 보조 이미지는 필요할 때 불러온다. 이미지의 비율을 유지하고 PC·모바일에서 내용을 임의로 잘라내지 않는다. 기존 이미지 확대 기능과 키보드 접근을 유지한다.

## 6. 기존 소개 슬라이드의 역할

기존 `pm-case-study_01.png`부터 `pm-case-study_08.png`까지의 자료는 2026-10-26 작성된 예시 데이터 기반 설명 자료다. 실제 서비스 화면과 구분하고, 페이지 하단의 기본적으로 닫힌 과거 참고 자료 영역에만 둔다.

과거 자료에 포함된 표현·검증 수치·날짜는 당시 기록의 범위로 안내한다. 이번 개편의 서비스 정의나 최신 성과를 대신 설명하는 대표 자료로 사용하지 않는다. 과거 ‘혜택 적용’ 중심 문구가 담긴 슬라이드를 상단 대표 이미지로 재사용하지 않는다.

## 7. 기술 및 검증 정합성

- 구현 기술은 기존 설명과 같이 FastAPI · Next.js · SQLite · Ollama를 기준으로 소개한다.
- 현재 원장 검색은 식별자 일치·어휘/BM25·조건 필터·관계 자료 연결을 사용한다. 의미 기반 벡터 검색이나 모델 학습을 현재 구현 성과로 추가하지 않는다.
- 기간·연식 등 명확한 조건의 답변은 규칙 기반으로 처리하고, 일반 질문에는 근거를 연결한 로컬 LLM 답변을 사용한다. 모든 답변을 LLM이 생성한다고 표현하지 않는다.
- 일반 사용자의 개인 대화·저장 답변과 관리자 검토·승인 기능의 책임을 구분한다.
- 자료 검토와 질문 수집이 자동으로 모델을 학습시키거나 정책을 승인한다는 표현을 사용하지 않는다.
- 기능 구현·기존 검사 기록과 실제 업무 답변 품질은 구분한다. 확인하지 않은 정확도·업무시간 절감·비용 개선 수치, 전사 도입 완료, SSO 또는 공개 서비스 운영 완료를 주장하지 않는다.

검증 범위 영역에는 질문 범위·근거·버전 연결, 자료 제안·검토·승인·적용일, 저장 답변의 근거 보존을 현재 소개 범위로 제시한다. 독립적인 업무 질문 평가, 잘못된 근거 선택·기간 예외, 정정 빈도, 인증·백업·복구·배포 검증은 추가 확인할 내용으로 설명한다.

기능 사실은 서비스의 README, ARCHITECTURE, STATUS와 실제 구현을 함께 대조한다. 청킹 설명은 원장 재생성 도구의 필드 분할·묶음·메타데이터·부모 연결 처리와 현재 DB 검색 구현을 각각 확인한다. 정책 추가 설명은 실제 작성·등록·검토 화면의 레이블과 파일 제한을 확인한다. 과거 개발 계획의 일정과 검증 수치를 이번 개편에서 새로 실행한 결과로 옮기지 않는다.

검증 메모: 이번 세션에서는 브라우저 캡처 연결을 사용할 수 없어 새 화면 촬영을 수행하지 못했다. 기존 2026-10-21 원본 캡처의 적용과 파일·내용·경로 검증을 새 촬영이나 브라우저 시각 검증의 완료로 표현하지 않는다.

## 8. 반영 완료 기준

1. 첫 화면에 설명 슬라이드 대신 마스킹 전 실제 답변 화면이 보이고, 2026-10-21 원본 캡처 사용 사실이 표시된다.
2. 서비스 이용자가 사내 임직원이며, 다루는 범위가 제네시스 전 차종의 혜택 오퍼링·프리빌리지·기프트 정책임을 소개와 메타 설명에서 확인할 수 있다.
3. 본문의 작업 방식 → 답변 구조 → 운영 방식 순서와 `#work`, `#answer`, `#operations`, `#scope` 이동이 유지된다.
4. 답변 내용뿐 아니라 조건·근거·당시 버전과 정책 검토·적용 시점을 함께 설명한다.
5. 네 원본 캡처의 JPG 경로·1440×1000 비율·대체 텍스트·캡션·확대 동작과 모바일 이미지 표시를 확인한다.
6. 기존 8장 슬라이드는 하단의 닫힌 참고 자료에만 남고, 과거 설명 자료라는 안내가 붙는다.
7. 미검토 원본의 사용 가능성, 규칙과 LLM의 역할, 현재 검색 방식에 대한 설명이 구현 사실과 일치한다.
8. `#chunking`에서 업무 레코드·고유 ID·필드명 반복·1,200자 분할·약 1,700자 묶음·부모 관계·메타데이터·변경 추적과 그 이유를 설명하고, 현재 BM25 기반 DB 검색과 전처리를 구분한다.
9. `#policy-add`에서 직접 작성·선택적 UTF-8 MD/TXT 가져오기·임시 저장·정보 등록하기·관리자 검토/승인·적용일 반영 절차와 실제 파일 제한을 확인할 수 있다.
10. 원본 화면에 이미 보이는 내용을 별도 텍스트로 새로 추출·인용하지 않으며, 이번에 수행하지 않은 새 촬영이나 품질 검증을 완료로 표현하지 않는다.

이 문서는 공개 포트폴리오의 구성과 문구를 위한 개편 기획서다. 서비스 자체의 정책·운영 데이터나 기능을 변경하는 작업은 포함하지 않는다.
