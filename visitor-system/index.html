문제 1

방문 신청과 실제 방문 기록은 같은 상태가 아니다

문제와 원인

현장에서 이미 도착한 방문자와 도착 전에 신청만 한 방문자를 한 목록·같은 상태로 처리하면, 운영자는 방문이 확정됐는지부터 다시 판단해야 합니다. 이 프로젝트가 풀려는 문제는 입력 폼을 만드는 것보다 신청·승인·방문·종료의 의미를 일관되게 연결하는 일이었습니다.

사전 신청에는 검토와 승인이라는 결정이 필요하지만 현장 등록은 즉시 방문 기록을 만들어야 합니다. 접수 정보만 저장하면 누가 승인했고 어떤 신청에서 방문 기록이 만들어졌는지 추적하기 어렵습니다.

선택한 해결과 이유

현장 등록은 방문 중 기록으로 저장하고, 사전 신청은 별도 접수 상태에서 승인·거절을 처리합니다. 승인 시 방문 예정 기록을 만들고 원본 신청번호와 연결하며, 처리자·처리 시간을 남깁니다.

운영 화면에서 상태를 보고 다음 행동을 고를 수 있게 하고, 방문 기록과 승인 판단의 근거를 함께 확인할 수 있도록 한 구조입니다. 서로 다른 접수 경로를 억지로 같은 절차에 맞추지 않으면서 최종 방문 관리로 연결합니다.

감수한 점

접수와 방문 기록을 분리한 만큼 승인 처리의 일관성과 중복 생성 방지가 중요해집니다. 현재 구조의 존재와 승인 요청이 동시에 들어와도 안전한지는 다른 문제입니다. 또한 방문 예정 시각이 지나면 대시보드 조회 시 방문 중으로 바꾸는 구현이므로, 이 상태를 실제 출입 감지 결과로 해석할 수 없습니다.

확인한 근거

구현 상세의 사전 신청·승인 이력, 데이터 구조의 원본 신청 연결, 상태 처리 규칙에서 확인됩니다. 공개 화면은 가상 방문 기록이며 전체 승인 시나리오의 운영 검증 결과는 아닙니다.

다음 확인

같은 신청의 반복 승인과 동시 승인에서 방문 기록이 한 건만 만들어지는지, 승인 이후 정보 변경을 허용할지, 실제 입실 확인을 어떤 동작으로 확정할지 검증하고 정책으로 정리해야 합니다.

문제 2

등록 직후의 작은 정정을 운영자에게만 맡기지 않기

문제와 원인

방문자는 현장에서 빠르게 입력해야 하지만 연락처나 차량번호를 잘못 입력할 수도 있습니다. 매번 관리자에게 정정을 요청하게 하거나 일회성 방문에 계정 가입을 요구하면 입력 이후의 부담이 커집니다.

계정 없는 방문자의 수정 요청은 누구의 기록인지 확인하는 수단이 필요합니다. 이름이나 전화번호만으로 수정 대상을 고르면 다른 사람의 기록을 변경할 수 있고, 수정 링크를 무기한 유지하면 접근 범위가 불필요하게 넓어집니다.

선택한 해결과 이유

등록 완료 후 같은 세션에 임의 수정 토큰과 만료 시각을 보관하고, 그 토큰으로 본인 기록만 제한된 시간 안에 수정하도록 연결합니다. 현재 수정 유효 시간은 10분이며 사전 신청의 초대 토큰은 별도로 2시간을 적용합니다.

일회성 방문에 계정 생성 단계를 더하지 않으면서, 등록 직후 정정이라는 좁은 목적에 필요한 수정 권한을 부여합니다. ‘접수 링크의 유효 시간’과 ‘등록 후 수정 가능 시간’을 다른 정책으로 다룬 점이 핵심입니다.

감수한 점

사용자가 브라우저나 세션을 바꾸면 같은 수정 흐름을 이어가기 어렵고, 시간이 지나면 운영자 도움이 필요합니다. 토큰의 존재만으로 보안 전체가 완성되는 것은 아니며, 재사용·만료·승인 이후 수정 규칙을 함께 확인해야 합니다.

확인한 근거

등록 완료 화면의 내용 수정 버튼, 본인 수정 라우트의 세션·토큰·만료 조건, 사전 초대 토큰의 시간 정책에 구현 근거가 있습니다. 실제 메일 수신과 토큰 만료 경계의 종단 검증은 별도 범위입니다.

다음 확인

정상 수정, 만료 직후 수정, 다른 세션 접근, 동일 토큰 반복 제출, 승인 후 수정의 다섯 시나리오를 구분해 확인하고 만료 후 안내와 관리자 정정 경로를 보완해야 합니다.

문제 3

방문 목록을 조회에서 후속 처리까지 이어지는 작업 화면으로

문제와 원인

운영자는 방문 정보가 있다는 사실만으로 업무를 끝낼 수 없습니다. 특정 방문을 찾아 승인·정정·종료하고, 누가 언제 처리했는지 확인할 수 있어야 합니다. 목록과 처리 기능이 분리되면 같은 대상을 반복해서 찾는 과정이 생깁니다.

방문일·예정일·입실·종료가 섞이고 기록이 늘어날수록 단순 표는 검색과 상태 판단에 불리해집니다. 관리 계정도 모두 같은 권한을 가지면 일반 운영과 계정 관리의 책임이 섞입니다.

선택한 해결과 이유

회사·이름·연락처·기간 검색과 페이지 단위 조회를 제공하고, 목록에서 상세 확인·수정·방문 종료로 연결합니다. 종료 시각과 처리자를 남기며, 관리자·운영자 등급과 대상 계정에 따른 계정 관리 범위를 구분합니다.

운영자의 반복 행동을 ‘대상 찾기 → 상태 확인 → 처리 → 이력 확인’으로 묶습니다. 입력 화면의 완성뿐 아니라 기록을 맡은 사람이 다음 행동을 수행할 수 있는지를 설계 범위에 넣었습니다.

감수한 점

한 화면에 처리 기능을 모으면 업무 연결은 좋아지지만 정보 밀도와 실수 가능성이 커집니다. 현재 데스크톱 목록에는 일부 말줄임이 있으며, 이름·연락처 마스킹은 화면 노출을 줄이는 표현일 뿐 접근 권한 검사나 개인정보 보관 정책을 대체하지 않습니다.

확인한 근거

관리자 방문자 목록·승인·계정 관리 화면, 검색과 종료 처리 코드, 역할별 관리 설명에서 확인됩니다. 로컬 앱 실행과 화면 렌더링은 확인했지만 모든 권한 조합·삭제·메일 실패까지 통과한 것으로 소개하지 않습니다.

다음 확인

역할별 직접 요청 차단, 종료 중복 요청, 선택 처리의 오조작 방지, 모바일 목록의 가독성, 보관·삭제 정책을 시나리오별로 검증해야 합니다.

프로젝트의 동작·설계 근거와 실제 사용 효과는 구분해 설명합니다.

방문자 화면은 최대 폭 460px의 컨테이너를 사용합니다. 필수 항목 표시, 전화번호 자동 하이픈, 목적 선택, 보안물품 상세 입력을 적용했습니다.

완료 화면에는 방문자 요약과 추가 등록·내용 수정 버튼을 배치했습니다. 사전 신청 폼에는 방문 날짜와 시간 입력을 추가했습니다.

상세 흐름 A · 현장 등록과 본인 수정
  1. 방문자가 등록 폼을 입력하고 개인정보 수집에 동의합니다.
  2. 서버가 현재 날짜·시간과 방문 중 상태를 저장합니다.
  3. 수정용 임의 토큰을 생성하고 세션에 기록 ID와 만료 시각을 보관합니다.
  4. 완료 화면에서 추가 등록 또는 내용 수정으로 이동합니다.
  5. 수정 요청 시 토큰과 만료 여부를 확인한 후 해당 기록을 갱신합니다.
상세 흐름 B · 사전 신청과 승인
  1. 관리자가 이메일을 입력하면 초대 토큰과 발신자 정보를 저장합니다.
  2. 방문자는 만료 전 초대 링크에 접속해 일정을 제출합니다.
  3. 신청은 승인 대기 상태로 저장되고 발신 관리자에게 접수 알림을 보냅니다.
  4. 승인 시 신청에 처리 정보를 남기고 방문 예정 기록을 생성합니다.
  5. 신청 이력과 방문 기록을 source_request_id로 연결합니다.
상세 흐름 C · 임시 비밀번호와 강제 변경
  1. 계정 정보와 이메일이 일치하는지 확인하고 인증번호를 보냅니다.
  2. 인증번호 확인 후 영문·숫자·특수문자가 포함된 임시 비밀번호를 생성합니다.
  3. 해시를 저장하고 force_password_change 표시를 설정한 뒤 메일을 보냅니다.
  4. 로그인 후 새 비밀번호 설정 화면으로 이동하도록 접근을 제한합니다.
  5. 새 비밀번호 확인·형식 검증이 끝나면 변경 표시를 해제합니다.
상세 흐름 D · 이메일 주소 변경
  1. 현재 등록된 이메일로 본인 확인 인증번호를 보냅니다.
  2. 인증 완료 상태를 확인한 다음 새 이메일의 중복 여부를 확인합니다.
  3. 새 주소로 별도의 인증번호를 보내 소유 여부를 확인합니다.
  4. 새 이메일과 인증번호가 일치하고 만료 전이면 주소를 변경합니다.
  5. 변경 완료 후 인증용 세션 정보를 정리합니다.
