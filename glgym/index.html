01 / THE PROBLEM

신청 버튼 뒤에는,
운영자가 지켜야 할 조건이 있습니다.

남은 자리만 보여 주는 예약을 넘어, 회원권·주간 횟수·수업 변경이 함께 맞물리는 업무를 다룹니다.

회원에게는 이번 주의 행동을

어느 날 어떤 수업에 참여하는지, 정원이 차면 대기할 수 있는지, 예약을 바꾸려면 어떤 절차가 필요한지 같은 기준이 필요합니다. 예약 상태와 수업 시간, 내 참여 여부를 함께 확인하도록 구성했습니다.

운영자에게는 반복 가능한 기준을

회원권 종류·참여 횟수·수업 정원·반복 시간표를 관리하고, 회원의 지정 수업시간 요청을 검토합니다. 일회성 예약 변경과 장기 고정 시간 변경을 구분해 기존 예약의 혼선을 줄이는 기준을 정했습니다.

서비스의 업무 구조와 현재 소스를 바탕으로 정리한 문제 정의입니다. 사용자 인터뷰나 개선 효과를 측정한 결과로 표현하지 않습니다.

문제 1

남은 자리만으로는 예약 가능 여부를 설명할 수 없다

문제와 원인

회원은 자리가 보이면 신청할 수 있다고 기대하지만 체육관 운영에서는 회원권 유효기간, 반 구분, 주간 횟수와 하루 참여 조건도 맞아야 합니다. 정원이 찬 수업은 취소 자리가 생겼을 때 누구를 먼저 참여시킬지도 정해야 합니다.

정원·참여 자격·대기 순서를 별개의 판단으로 두면 화면의 신청 안내와 운영자의 처리 기준이 어긋날 수 있습니다. 대기 신청을 주간 한도에 포함하는지 불명확하면 참여 기회를 여러 수업에 중복 점유하는 문제도 생깁니다.

선택한 해결과 이유

회원권·반·횟수 조건을 확인한 뒤 참여 또는 대기 상태로 연결합니다. 참여와 대기를 주간 신청 횟수에 함께 포함하고, 취소로 자리가 나면 신청 시각 순서대로 빈 자리 수만큼 대기를 참여로 전환하는 기준을 둡니다.

신청 버튼의 활성 여부부터 취소 후 후속 처리까지 같은 운영 기준으로 설명하기 위한 구조입니다. 화면에는 신청 인원과 정원, 대기 상태를 나누어 보여주고 명단 확인으로 연결합니다.

감수한 점

대기도 한도에 포함하면 기회 중복 점유를 제한할 수 있지만, 대기 중인 회원은 다른 수업을 잡기 어렵다고 느낄 수 있습니다. 신청 순서 승격은 이해하기 쉽지만 동시 신청·취소와 알림 실패에서도 순서와 정원이 유지되는지 별도로 검증해야 합니다.

확인한 근거

수업 신청 API와 운영정책에서 회원권·횟수·정원·대기 기준을 확인했습니다. 공개 PC·모바일 화면은 원본 UI를 가상 읽기 응답으로 렌더링한 것이며 실제 예약·승격 서버 로직의 통과 증거가 아닙니다.

다음 확인

마지막 한 자리에 대한 동시 신청, 대기 중복 제출, 여러 자리 취소, 승격 직전 회원권 만료와 알림 실패를 구분해 데이터와 안내의 일관성을 확인해야 합니다.

문제 2

‘이번 주 변경’과 ‘앞으로의 고정 시간 변경’을 나누기

문제와 원인

회원이 수업을 바꾸고 싶다고 해도 이번 주 한 번만 옮기는지, 앞으로 매주 다닐 고정 시간을 바꾸는지는 다른 요청입니다. 승인 즉시 모든 예약에 반영하면 이미 잡힌 수업과 다음 주 시간표가 섞일 수 있습니다.

수업 한 건의 예약과 반복 시간표는 적용 범위가 다르며, 관리자의 승인 완료 시점과 실제 수업에 반영되는 시점도 같지 않습니다. 이 차이를 화면과 상태에 남기지 않으면 회원과 관리자가 서로 다른 ‘완료’를 이해하게 됩니다.

선택한 해결과 이유

이번 주만 바꾸는 예약과 지정 수업시간 변경 요청을 구분합니다. 지정시간의 첫 설정은 승인 즉시, 기존 지정시간 변경은 승인 후 다음 주부터 적용하며 검토 대기·승인 후 적용 대기·반영 완료를 나누어 안내합니다.

현재 예약을 보존하면서 반복 일정의 변경을 운영자가 검토할 수 있도록 한 기준입니다. ‘승인했는데 왜 아직 안 바뀌었는가’라는 상황을 오류가 아닌 예정된 적용 상태로 설명할 수 있습니다.

감수한 점

항상 즉시 반영하는 방식보다 대기 상태와 주간 경계 처리가 늘어납니다. 다음 주 적용은 현재 예약의 혼선을 줄이는 선택이지만, 주 경계 직전 요청·중복 승인·회원권 조건 변경을 다루는 규칙이 더 명확해야 합니다.

확인한 근거

지정 수업시간 요청 화면과 운영정책에는 첫 설정·기존 변경의 적용 시점 차이, PENDING·APPROVED_PENDING·APPROVED 상태가 정리돼 있습니다. 공개 캡처의 변경 폼은 가상 데이터 화면 확인입니다.

다음 확인

일요일·월요일 경계의 승인, 같은 요청의 반복 승인, 적용 대기 중 재요청, 변경 전 예약의 취소·유지를 시나리오별로 검증해야 합니다.

문제 3

운영자가 바꿀 수 있는 설정과 시스템 규칙을 구분하기

문제와 원인

회원권과 시간표를 운영할 때 모든 예외를 매번 담당자의 기억으로 처리하면 안내가 달라질 수 있습니다. 반대로 모든 조건을 관리자 설정으로 열면 핵심 운영 규칙을 의도치 않게 바꾸기 쉬워집니다.

회원권 종류·기간·횟수·수업 정원처럼 운영 중 바뀌는 값과 취소 마감·대기 제한 같은 공통 규칙은 성격이 다릅니다. 일반 회원·코치·관리자도 가능한 행동과 정원 집계 방식이 같지 않습니다.

선택한 해결과 이유

회원·회원권·반복 시간표·변경 요청 검토를 각 관리 화면으로 나누고, 관리자 화면에서 변경 가능한 값과 코드에 고정된 규칙을 문서에서 구분합니다. 신청 가능 조건과 취소 가능 조건도 분리하며 역할에 따른 예외를 적용합니다.

운영자가 일상적으로 바꾸는 정보와 서비스가 지켜야 할 공통 약속을 나누어 설명하기 위해서입니다. 회원과 관리자의 화면은 달라도 동일한 회원권·수업·상태를 기준으로 처리하도록 구성했습니다.

감수한 점

고정 규칙의 변경에는 코드 배포가 필요하고, 설정 화면을 나누면 관리자가 여러 화면을 오갈 수 있습니다. 현재 원본은 PC에서도 약 512px 중심의 모바일 우선 레이아웃이므로 대량 회원·시간표를 비교하는 업무에 충분한지는 별도 사용 검증이 필요합니다.

확인한 근거

회원·관리자 원본 화면과 운영정책, 역할·회원권·시간표 데이터 구조가 근거입니다. 시스템은 오프라인 회원권 계약 정보를 관리하며 온라인 결제를 수취하는 서비스로 소개하지 않습니다.

다음 확인

운영자에게 회원권 등록·시간표 수정·변경 승인 과제를 주고 재문의와 잘못된 설정이 발생하는 지점을 관찰해야 합니다. 실사용 빈도가 높은 규칙만 설정으로 열 필요가 있는지 판단해야 합니다.

프로젝트의 동작·설계 근거와 실제 사용 효과는 구분해 설명합니다.

관리자의 운영을 같은 기준으로.

같은 수업을 서로 다른 역할에서 확인하고 처리합니다. 회원권은 오프라인 계약 정보를 관리자가 등록하며, 온라인 결제 수취 기능은 포함하지 않습니다.

MEMBER / 01

03

ADMIN / 04

운영 검토

적용과 안내

승인 여부와 반영 시점을 회원에게 전달합니다.

같은 ‘변경’도 적용 범위가 다릅니다.이번 주만 바꾸는 예약은 해당 주에만 적용됩니다. 지정 수업시간의 첫 설정은 승인 즉시, 기존 지정 시간 변경은 승인 후 다음 주부터 반영하도록 구분했습니다.
03 / KEY DECISIONS

정원·시간·상태를
화면의 동작 규칙으로 옮겼습니다.

아래는 소스와 운영정책에서 확인한 구현 기준입니다. 이번 화면 캡처 작업에서 모든 서버 업무 처리를 재검증했다는 의미는 아닙니다.

01

참여와 대기를 같은 신청 흐름에

일반 회원 정원이 차면 대기로 접수하고, 취소로 자리가 생기면 신청 순서에 따라 빈 자리 수만큼 참여로 전환합니다. 대기 상태도 주간 신청 횟수에 포함합니다.

상태 기준ATTENDING · WAITING · CANCELED를 구분합니다. 정원과 대기 숫자를 따로 보여 주고 명단으로 이어집니다.
02

신청 가능성과 취소 가능성을 분리

회원권 유효기간, 반 구분, 주간 횟수와 하루 1회 조건을 함께 적용합니다. 일반 회원의 취소는 수업 시작 90분 전까지이며 역할에 따른 예외를 구분합니다.

시간·권한 기준같은 버튼이라도 수업 시각과 역할에 따라 가능한 행동이 달라집니다. 조건을 서버에서 다시 확인하는 구조입니다.
03

승인과 실제 반영 사이의 상태를 표시

고정 시간 변경을 승인하더라도 이번 주의 예약과 바로 섞지 않습니다. 처음 지정하는 경우와 기존 시간을 바꾸는 경우를 구분하고 다음 주 적용 대기를 별도 상태로 다룹니다.

적용 시점PENDING → APPROVED_PENDING → APPROVED. 승인 완료와 현재 수업 반영 완료를 같은 것으로 안내하지 않습니다.
04

운영 설정과 고정 규칙을 나누기

회원권 종류·참여 횟수·기간, 수업 시간표·정원은 관리자 화면에서 관리합니다. 취소 마감과 대기 제한 같은 코드 규칙은 운영 문서에 구분해 남겼습니다.

관리 경험회원 검색·필터와 회원권, 반복 시간표, 변경 요청 검토를 각 업무 화면으로 나눴습니다.
04 / ACTUAL INTERFACE

원본 화면을 실행해,
PC와 모바일로 확인했습니다.

원본 Next.js UI와 스타일을 격리 환경에서 렌더링한 캡처입니다. 이름·이메일·회원권·예약 정보는 공개용 가상 예시이며 실제 운영 기록이 아닙니다. 이미지를 누르면 확대됩니다.

PC에서도 원래의 모바일 우선 구조를 유지합니다.현재 제품은 회원·관리자 화면 모두 최대 폭 약 512px의 컨테이너를 사용합니다. 캡처를 위해 별도의 넓은 데스크톱 화면을 새로 그리지 않았습니다.

캡처 환경의 API는 가상 읽기 응답이며 원본 인증·DB·메일·푸시와 연결하지 않았습니다. 캡처는 화면 구현의 근거이며 운영 업무의 완료나 전체 기능 통과를 증명하지 않습니다.

06 / EVIDENCE & BOUNDARIES

구현의 근거와
운영 검증의 범위를 구분합니다.

소스·문서에서 확인한 동작과 공개용 캡처에서 확인한 화면은 서로 다른 근거입니다.

소스·화면 확인

이번 사례가 보여 주는 범위

  • 회원과 관리자 화면, 역할·회원권·예약·대기 상태의 구현 구조.
  • 대기 승격, 취소 제한, 고정 수업시간 승인·적용 시점의 소스와 운영정책.
  • 원본 UI를 가상 응답으로 렌더링한 PC·모바일 캡처.
  • 실제 회원 정보와 원본 업무 서버를 사용하지 않는 공개 자료 구성.
별도 검증 대상

더 확인할 운영 조건

  • 동시 신청·취소 때 정원과 대기 순서의 일관성.
  • 중복 요청·승인·재시도와 주간 리셋의 경계 조건.
  • 실제 회원권 만료·수업 변경·알림 수신의 전체 시나리오.
  • 운영 인증·개인정보 보관·백업·복구와 실사용 흐름.

기능 통과율, 예약 처리시간 절감률, 이용 회원 수, 개인 기여율 등 검증하지 않은 성과 수치는 기재하지 않았습니다.

07 / TAKEAWAYS

예약 화면의 완성은,
운영 예외를 설명하는 데 있습니다.

자리가 있는지 보여 주는 화면에서 출발해 누가 신청할 수 있는지, 언제 취소할 수 있는지, 승인한 변경이 어느 수업부터 반영되는지를 같은 기준으로 연결한 사례입니다.

상태를 구분하면 안내도 구체적입니다.

참여와 대기, 검토 대기와 적용 대기를 따로 다루면 사용자는 현재 가능한 행동을 판단할 수 있습니다. 이 구분은 데이터 상태와 화면 문구가 함께 지켜야 하는 약속입니다.

다음은 실제 업무 흐름의 확인입니다.

동일한 가상 회원권·시간표 조건으로 신청·대기·변경 과제를 수행하고, 혼선과 재문의·수정이 생기는 지점을 관찰하는 것이 다음 개선의 기준입니다.

자료 기준과 공개 화면 안내

근거: 프로젝트 소스, Prisma 스키마, GLGYM 운영정책 및 프로세스 문서. 문서의 정리일과 이번 포트폴리오 정리일은 다릅니다.

화면은 원본 UI를 격리 환경에서 실행하고 공개용 가상 데이터로 캡처했습니다. 실제 서비스 운영 기록, 회원 개인정보, 인증정보를 포함하지 않습니다. 원본 서비스와 공개 포트폴리오의 역할은 구분됩니다.
