01 / SHORT STORY

약 1분으로 소개하기.

MJ Dashboard는 일정·메모·이메일·콘텐츠 작업처럼 흩어진 개인 업무를 파악하고 이어서 처리하는 작업 공간입니다. 이 사례의 중심은 정보를 많이 모으는 것보다, 홈에서 지금 확인할 일을 찾고 상세에서 같은 맥락으로 실행하게 하는 데 있습니다. 홈은 요약, 상세는 검색과 편집으로 역할을 나누고 날짜와 출처를 이어줬습니다. 같은 메모가 달력과 할 일에 보일 때도 별도 사본을 만들지 않고 원본의 식별자와 상태를 유지합니다. 저장에서는 오래된 화면의 덮어쓰기, 백업 실패, 저장 후 백업 대기를 구분해 개인 기록을 보호하는 기준을 다뤘습니다. 근거는 제품 문서와 코드, 격리된 저장·화면 검증 기록입니다. 사용자 생산성이 얼마나 좋아졌는지는 별도 비교 실험이 필요한 단계입니다.

02 / WALKTHROUGH

약 3분으로 작업 과정을 설명하기.

  1. 0:00–0:40 · 문제: 정보를 모은 뒤에도 사용자가 다시 우선순위를 골라야 하는 상황을 설명한다. 개인 사용 맥락의 문제 가설이며 보편적 사용자 조사 결과라고 말하지 않는다.

  2. 0:40–1:20 · 홈과 상세: 홈에서 가까운 일정을 보고 특정 날짜·출처의 상세로 이동하는 대표 동선을 보여준다. 왜 홈에 긴 목록과 편집 폼을 모두 넣지 않았는지 설명한다.

  3. 1:20–2:10 · 원본 연결: 날짜가 있는 메모 한 건을 홈·달력·할 일에서 보여주며 사본 생성이 아니라 같은 식별자의 다른 보기라는 점을 설명한다. 날짜 연결 해제와 기록 삭제도 구분한다.

  4. 2:10–3:00 · 신뢰와 검증: 오래된 버전 저장, 저장 전 백업 실패, 저장 후 백업 대기를 각각 설명한다. 샘플 화면과 개인 서버 저장 검증을 나누고, 다음에는 과제 수행 시간과 누락을 비교할 계획이라고 마무리한다.

03 / QUESTIONS & ANSWERS

판단의 이유를 묻는 질문.

Q1일반 대시보드와 차별점이 무엇인가요? 기능을 한곳에 모은 것뿐 아닌가요?

차별화 가설은 수집한 정보의 양보다 홈에서 다음 행동을 찾고 같은 원본의 상세로 이어지는 기준입니다. 홈과 상세의 역할, 날짜·출처의 유지, 기록의 중복 생성 방지와 저장 상태를 함께 설명할 수 있습니다. 다만 이 구조만으로 기존 도구보다 생산성이 높다고 단정하지 않고, 같은 과제를 수행하는 비교 실험으로 검증해야 합니다.

함께 제시할 근거

홈·상세 역할과 원본 연결 장, 제품 구조 문서의 요약·상세 이동 기준.

Q2달력에는 같은 메모를 복사해서 보여주면 더 간단하지 않나요?

처음 구현은 간단할 수 있지만 제목·날짜·완료 상태가 서로 어긋날 때 어떤 것이 기준인지 관리해야 합니다. 현재 구조는 원본의 식별자와 출처를 일정용 보기로 유지하고 수정도 원본에 반영합니다. 다만 출처별 데이터와 완료 규칙을 공통 보기에 연결해야 하므로, 단순히 화면에서 같은 문구를 보여주는 것보다 연결 계약의 검증이 중요합니다.

함께 제시할 근거

일정 모듈의 collection:row.id 키와 원본 row 유지, 날짜 연결 해제 시 원본 보존.

Q3revision 충돌을 거절하면 사용자가 작업을 잃는 것 아닌가요?

목적은 오래된 화면이 최신 기록을 조용히 덮어쓰는 것을 막는 것입니다. 현재 기준은 버전이 맞지 않으면 충돌을 알려 다시 판단하게 하는 방식입니다. 그 과정에서 입력 중인 초안을 어떻게 보존하고 차이를 확인하게 할지는 별도 UX 과제입니다. 실시간 공동 편집이나 자동 병합을 이미 구현한 것으로 설명하지 않고, 개인 작업 공간에서 무조건 덮어쓰기보다 안전한 기준을 택한 것으로 설명합니다.

함께 제시할 근거

저장·백업 기준의 revision 충돌 409 계약, 공개 사례의 충돌 상태 안내.

Q4저장됐는데 백업이 pending이면 성공인가요, 실패인가요?

원본 저장이 끝났는지와 독립된 백업 확정이 끝났는지를 분리합니다. D1 저장 성공 뒤 새 백업 확정이 실패했다면 저장은 성공이고 백업 확인이 남은 상태입니다. 반대로 저장 전 복구 지점 확보가 실패하면 원본 변경을 중단하는 기준이 있습니다. 두 상황을 모두 저장 실패라고 안내하면 중복 재시도나 잘못된 복구 판단을 만들 수 있습니다.

함께 제시할 근거

BACKUP-STORAGE의 사전 백업 실패와 저장 후 pending 처리 기준.

Q5데이터를 분할해 저장한 이유와 단건 저장으로 바꿀 때의 주의점은 무엇인가요?

기존 전체 스냅샷 경로에서는 DB 전체 용량이 아니라 한 행·문자열의 크기 제한이 문제였기 때문에, 논리적 JSON과 revision 계약을 유지하면서 헤더와 조각을 함께 저장하는 방식이 기록돼 있습니다. 읽을 때 조각 수·순서·바이트·해시를 확인합니다. 이후 메모·일정의 단건 저장을 추가하는 전환에서도 전체 조회·백업·복원이 같은 최신 원본을 사용해야 합니다. 내부 보관 구조를 바꾼다고 복구 보장이 자동으로 같아지는 것은 아닙니다.

함께 제시할 근거

저장·백업 문서의 대용량 분할 저장 배경과 2026-11-03 단건 저장 전환 기준.

Q648.4% 개선은 실제 속도가 48.4% 빨라졌다는 뜻인가요? 본인이 한 기여는 무엇인가요?

아닙니다. 공개 사례의 수치는 2026년 10월 동일 조건 빌드에서 초기 JavaScript gzip 합계를 비교한 값입니다. 화면 로딩 시간이나 실기기 체감 속도 개선율은 아닙니다. 개인 기여를 말할 때도 프로젝트의 모든 설계·코드를 단독 담당했다고 확대하지 않고, 실제 수행한 정보 구조·상태 정책·구현·검증 항목과 작업 기록을 구분해 제시해야 합니다.

함께 제시할 근거

공개 사례의 초기 JS 525,759B → 271,248B 비교 주석, 역할·검증 경계.
