01 / SHORT STORY

약 1분으로 소개하기.

이 프로젝트는 QR 현장 등록과 이메일 사전 신청을 관리자 운영으로 연결한 방문자 관리 웹 서비스입니다. 핵심 문제는 방문 정보를 입력받는 것 자체보다, 신청만 한 사람과 실제 방문 중인 사람을 구분하고 승인·수정·종료 이력을 같은 기준으로 관리하는 것이었습니다. 그래서 현장 등록은 즉시 방문 기록으로 만들고, 사전 신청은 승인 대기에서 검토한 뒤 방문 예정 기록과 연결했습니다. 계정 없는 방문자의 등록 직후 정정은 세션과 만료 토큰으로 제한하고, 운영 화면에서는 검색·상세·종료 처리를 이어줍니다. 현재 설명할 수 있는 근거는 구현 코드와 가상 데이터로 캡처한 실제 화면입니다. 중복 승인과 동시 요청, 실제 메일 수신과 권한별 예외는 별도 검증이 필요하며, 업무시간 절감 수치를 확인한 프로젝트로 설명하지는 않습니다.

02 / WALKTHROUGH

약 3분으로 작업 과정을 설명하기.

  1. 0:00–0:40 · 사용자와 문제: 방문자에게는 빠른 현장 입력과 도착 전 신청, 운영자에게는 승인 여부와 현재 방문 상태의 확인이 필요하다고 설명한다. 이는 현재 업무 구조에서 도출한 문제 정의이며 사용자 인터뷰 결과로 말하지 않는다.

  2. 0:40–1:30 · 대표 흐름: QR 현장 등록 한 건과 이메일 사전 신청 한 건을 나란히 설명한다. 현장은 방문 중 기록으로, 사전 신청은 승인 대기로 저장되고 승인 후 원본 신청번호와 연결된 방문 예정 기록을 만든다는 차이를 보여준다.

  3. 1:30–2:20 · 판단과 절충: 접수·방문 분리, 등록 후 10분 수정, 관리자 역할 구분을 선택한 이유와 그에 따른 중복 처리·세션 전환·정보 밀도 과제를 설명한다. 실제 입실 감지와 시간에 따른 상태 전환을 구분한다.

  4. 2:20–3:00 · 근거와 다음 단계: 실제 템플릿 7종과 기능 코드가 근거임을 보여주고, 전체 시나리오·동시성·메일·권한·보관 정책의 후속 검증을 제시한다. 본인이 수행한 기획·구현·검증 항목은 확인한 범위만 따로 말한다.

03 / QUESTIONS & ANSWERS

판단의 이유를 묻는 질문.

Q1방문 신청과 방문 기록을 왜 분리했나요? 한 테이블로도 가능하지 않나요?

한 테이블도 가능한 대안입니다. 다만 현재 구조는 승인 전 접수와 실제 운영할 방문 기록의 의미를 구분하고, 승인된 기록에서 원본 신청과 처리 이력을 찾아갈 수 있게 합니다. 대안 비교의 기준은 테이블 개수보다 상태 전이와 감사 이력이 명확한지입니다. 분리로 인해 승인 시 두 기록의 연결이 생기므로 원자적 처리와 중복 승인 방지가 후속 검증의 핵심입니다.

함께 제시할 근거

사전 신청·방문 데이터 구조, 원본 신청번호 연결, 승인·거절 이력 설명.

Q2QR만 스캔하면 등록할 수 있는데 본인 수정은 어떻게 제한하나요?

등록 이후 같은 세션에 보관한 임의 토큰과 만료 시간을 확인해 본인 기록의 짧은 정정 흐름으로 제한합니다. 현재 유효 시간은 10분입니다. 계정 가입의 부담을 줄이는 대신 다른 브라우저에서 이어가기 어렵다는 절충이 있습니다. 전화번호를 안다고 수정할 수 있는 구조로 설명하지 않고, 만료·재사용·다른 세션·승인 이후 변경을 각각 점검해야 합니다.

함께 제시할 근거

본인 정보 수정 흐름, 세션의 수정 토큰과 만료 조건.

Q3방문 중 인원은 실제 건물 안의 인원과 같나요?

현재 구현의 방문 상태와 실제 출입 감지는 구분해야 합니다. 현장 등록은 방문 중으로 저장하고, 승인된 방문 예정 기록은 예정 시각이 지나 대시보드를 조회할 때 방문 중으로 전환합니다. 실제 출입 장치가 입실을 확인한 결과는 아닙니다. 운영 정확도를 높이려면 입실 확인 주체와 동작을 먼저 정하고 상태 전이와 집계 기준을 바꿔야 합니다.

함께 제시할 근거

상태 처리 규칙의 대시보드 조회 시 전환 안내.

Q4마스킹과 관리자 로그인만 있으면 개인정보 보호가 충분한가요?

충분하다고 말할 수 없습니다. 마스킹은 목록에서 노출을 줄이는 UI이고, 서버의 인증·권한 검사와 보관·삭제 정책은 별도입니다. 현재 구현의 역할별 관리 범위를 설명하되 직접 요청으로 다른 대상의 정보를 바꿀 수 없는지, 로그와 백업에는 무엇이 남는지, 어떤 시점에 기록을 지울지까지 운영 기준으로 확인해야 합니다.

함께 제시할 근거

방문자 목록 마스킹, 등급별 계정 관리, 후속 개인정보·권한 검증 범위.

Q5이미 구현됐는데 왜 검증 완료라고 하지 않나요?

코드가 존재하고 화면이 렌더링된 것과, 외부 메일·만료·동시 요청까지 포함한 업무 흐름이 통과한 것은 다른 근거이기 때문입니다. 현재는 로컬 실행·DB 연결과 대표 화면 확인의 범위를 제시합니다. 다음에는 등록 → 수정 → 승인 → 종료를 정상·중복·실패 조건으로 나누고 결과 데이터와 처리 이력까지 확인해야 합니다.

함께 제시할 근거

포트폴리오의 실행·화면 확인과 후속 시나리오 검증 구분.

Q6이 프로젝트에서 본인이 맡은 것은 정확히 무엇인가요?

프로젝트 전체 범위는 방문자·관리자 화면, Flask 업무 처리, MariaDB 상태 저장, 이메일·QR 연동입니다. 제가 직접 맡은 범위는 [확인된 기획·구현·검증 담당 항목]이고, 대표 사례는 [직접 수행한 작업과 근거]입니다. 프로젝트 전체 기능과 제 개인 기여는 이 담당 범위로 구분합니다.

함께 제시할 근거

프로젝트 범위와 문서 기준에 명시된 미확인 항목.

04 / ROLE & EVIDENCE

내 역할과 확인한 범위를 구체화하기.

프로젝트의 구현 범위는 확인되지만 개인별 담당·팀 구성·개발 기간은 확정되지 않았다. 설명 준비 시 ‘문제·정책 정리 / 화면 구현 / 서버·DB / 이메일·QR / 검증’별로 실제 수행 여부와 증빙을 채운다.

면접 전에 확인할 것

  • 사전 신청과 현장 등록의 상태 차이, 원본 신청 연결을 화면과 데이터 양쪽에서 설명할 수 있는가?
  • 10분·2시간 정책의 목적과 만료 후 처리 경로를 설명할 수 있는가?
  • 예정 시각 경과가 실제 출입 감지가 아니라는 한계를 말할 수 있는가?
  • 본인의 실제 작업 파일·커밋·검증 기록을 프로젝트 전체 범위와 분리하고 역할 답변의 빈칸을 확인된 항목으로 채웠는가? 원래 기획 원문과의 대조, 개발 기간·팀 규모·기여율은 기록으로 확인했는가?
  • 메일 수신·권한·중복 승인 등 미검증 항목을 완료 성과로 말하지 않는가?

  • 승인 이후 수정과 실제 입실 확정 주체에 대한 운영 정책 합의.

  • 운영자 과제 수행 시간·정정 빈도·처리 누락을 같은 조건에서 비교하는 사용자 검증.
