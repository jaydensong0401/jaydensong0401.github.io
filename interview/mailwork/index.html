01 / SHORT STORY

약 1분으로 소개하기.

Mailwork는 메일을 요약하는 데서 끝나지 않고, 대화 속 요청을 실행할 업무로 연결하는 개인 업무 도구입니다. 문제는 메일을 읽은 뒤에도 담당과 기한, 최신 결정을 다시 골라야 한다는 점으로 정의했습니다. 대화를 묶어 할 일·담당·기한을 정리하고 오늘·프로젝트·일정에서 같은 업무를 보게 했습니다. 특히 AI의 분석 결과와 사용자의 완료·제외·직접 기한을 분리해, 자동 정리가 사람의 판단을 덮어쓰지 않도록 하는 기준을 다뤘습니다. 명확한 분류는 규칙으로, 문맥 이해는 AI로 나눴습니다. 공개 데모에서는 가상 데이터의 흐름을 확인할 수 있지만, 실제 정확도나 시간 절감률은 아직 별도 측정이 필요한 범위로 구분합니다.

02 / WALKTHROUGH

약 3분으로 작업 과정을 설명하기.

  1. 메일 읽기와 업무 판단의 차이

    메일이 많다는 설명에 머무르지 않고, 회신 사이에 바뀐 요청·담당·기한을 다시 판단해야 하는 장면을 설명합니다. 사용자 인터뷰나 관찰 결과가 따로 없다면 개인 업무에서 세운 문제 가설이라고 밝힙니다.

    근거 · 같은 대화의 요청 변경을 담은 가상 메일 사례

  2. 메일 → 대화 → 업무 → 화면

    대화 연결을 먼저 하고 업무를 구조화한 이유를 말합니다. 오늘 화면의 기한과 프로젝트 화면의 결정사항이 같은 업무를 다른 목적에 맞춰 보여준다는 점을 이어서 설명합니다.

    근거 · 공개 데모 오늘·프로젝트·일정

  3. AI와 사람의 상태 분리

    완료한 일을 새 분석이 되살리는 상황을 예로 듭니다. 완료·제외·복구·직접 기한을 별도로 다루는 기준과, 제외 후 다시 지목된 요청을 알리는 예외를 설명합니다.

    근거 · 완료·제외·복구와 직접 기한 변경 동작

  4. 전부 AI로 처리하지 않은 이유

    분류 규칙 변경과 문맥 분석의 목적이 달라 분리했다는 설계상 이점을 설명합니다. 증분 분석은 입력량을 줄일 수 있지만 맥락 누락을 확인해야 한다는 대가도 함께 말합니다.

    근거 · 메일 분류 규칙·사용 현황 페이지

  5. 동작 증거와 실사용 성과를 구분

    공개 샘플에서 확인 가능한 동작을 보여주고, 실제 메일 추출 품질·업무시간 개선은 측정하지 않은 상태라면 수치로 주장하지 않습니다. 다음 실험은 누락·잘못된 담당·정정 비율을 먼저 보는 것으로 제안합니다.

    근거 · 가상 데이터 데모와 후속 평가 계획

03 / QUESTIONS & ANSWERS

판단의 이유를 묻는 질문.

Q1기존 메일 요약 도구와 무엇이 다른가요?

차이를 요약 문장의 품질만으로 설명하지 않겠습니다. Mailwork가 다룬 단위는 대화에서 파생된 업무이고, 담당·기한·결정사항을 오늘·프로젝트·일정의 행동으로 연결합니다. 사용자의 완료·제외·복구가 분석 결과와 다른 상태라는 점이 핵심 설계입니다. 다른 도구보다 우수하다는 비교 결과는 없으므로 제품 간 성능 우위를 주장하지 않습니다.

함께 제시할 근거

공개 데모의 동일 업무·상태 연결

Q2왜 모든 분류를 AI에게 맡기지 않았나요?

프로젝트 분류에는 제목 키워드·태그·도메인처럼 설명 가능한 조건이 있습니다. 이 영역을 규칙으로 두면 규칙 변경만으로 분류를 다시 적용할 수 있고, AI는 담당과 요청 변화처럼 문맥 이해에 집중할 수 있습니다. 대신 규칙을 관리할 부담과 새로운 표현의 예외가 생기는 절충이 있습니다. 규칙 분류와 전체 AI 분류를 비교한 실험 결과는 현재 확인되지 않았습니다.

함께 제시할 근거

분류 규칙과 업무 분석의 별도 경로

Q3새 메일을 분석하면 완료나 제외가 초기화되지 않나요?

그 위험 때문에 사용자 피드백을 메일·분석 자료와 별도로 보관하고 직접 기한도 우선 적용합니다. ‘남의 일’과 ‘할 일 아님’은 분석 제외 규칙에 연결하고, 이후 다시 받는사람으로 지목되면 새 요청 사실을 알립니다. 다만 업무 문구가 바뀌거나 분할되는 모든 상황의 연결이 완벽하다고 말하지 않고, 식별자 변경과 복구를 별도 검증 항목으로 설명하겠습니다.

함께 제시할 근거

피드백 별도 저장·기한 우선·다시 지목 알림

Q4메일 데이터가 외부로 나가거나 자동으로 발송되나요?

공개 데모는 실제 메일함이나 AI에 연결하지 않습니다. 실제 구현의 메일 접근은 읽기 전용이며 화면의 완료·제외는 메일을 삭제하거나 옮기는 동작과 구분됩니다. 화면과 저장은 로컬 중심이지만 분석에 어떤 엔진을 쓰는지에 따라 본문 전송 경로는 달라집니다. 따라서 모든 구성에서 데이터가 PC 밖으로 절대 나가지 않는다고 단정하지 않겠습니다.

함께 제시할 근거

공개 샘플 안내·읽기 전용 수집·분석 엔진 구분

Q5얼마나 정확하고 얼마나 시간을 줄였나요?

현재 소개 근거로 확인할 수 있는 것은 화면 동작·상태 규칙·사용량 기록입니다. 실사용 정확도와 업무시간 절감률은 독립적인 정답 대화 세트와 비교 실험이 있어야 답할 수 있습니다. 다음에는 누락·담당 오판·기한 오류·수동 정정 비율을 먼저 측정하고, 같은 업무를 원본 메일과 도구로 처리할 때의 시간과 재확인 횟수를 비교하겠습니다.

함께 제시할 근거

기능 확인과 실사용 효과 검증의 구분

Q6다시 만든다면 무엇부터 바꾸겠나요?

화면 수를 먼저 늘리기보다 업무가 바뀌었을 때 기존 사용자 판단을 어느 업무로 이어 붙일지 확인하겠습니다. 요청 번복, 한 업무의 분할, 제외 후 새 요청처럼 신뢰를 흔드는 사례를 평가 세트로 만들고 원문으로 돌아가 정정하는 동선을 살피겠습니다. 그 결과를 본 뒤 증분 분석 범위와 상태 연결 방식을 조정하는 순서가 타당합니다.

04 / ROLE & EVIDENCE

내 역할과 확인한 범위를 구체화하기.

현재 확인된 자료는 프로젝트의 코드·화면·설계 기준입니다. 개인이 직접 수행한 기획·구현·검증 범위와 협업 여부는 별도 확인이 필요합니다. 역할을 확정하기 전에는 ‘모두 혼자 만들었다’거나 각 설계 판단을 모두 본인의 독자 결정으로 표현하지 않습니다.

면접 전에 확인할 것

  • 직접 맡은 화면·상태 정책·구현·검증과 도움받은 작업을 구분하기
  • 개발 기간과 실제 사용 기간을 기록으로 확인하기
  • 문제 가설을 세운 실제 업무 장면 한 가지를 준비하기
  • 완료·제외·복구·기한 변경을 데모에서 직접 설명할 수 있게 연습하기
  • 당시 검토한 대안이 있었는지 확인하고 사후 제안과 구분하며, 비교 실험은 실제 기록이 있는 범위만 설명하기
  • 테스트 통과 기록과 실제 업무 정확도·시간 절감 수치를 구분하기
