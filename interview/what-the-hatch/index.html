01 / SHORT STORY

약 1분으로 소개하기.

What the Hatch?!는 계란을 굴리며 성장하고, 지나온 여정과 속성에 따라 생명체를 부화시키는 3인 팀 게임입니다. OpenAI Game Builders Seoul 참여작이며, 제 작업은 2026년 9월 3일에 정리한 개인 제작 이력을 기준으로 설명합니다. 저는 속성의 획득·장착·효과·조합과 작명 규칙을 연결하고, 부화장 상호작용과 부활 흐름을 개선했습니다. 대표적으로 부화장 앞에서 입력해도 반응하지 않는 문제를 단순한 거리 문제가 아니라 진행 조건·입력 전달·노드 초기화 문제로 나누어 수정했습니다. 또 부활을 좌표 이동이 아니라 크기와 속도를 포함한 상태 복원으로 다뤘습니다. 전체 월드와 기본 게임 루프, 최종 통합·배포는 팀의 결과입니다. 제 기여는 추상적인 콘셉트를 보이는 선택과 일관된 동작으로 구체화한 부분입니다.

02 / WALKTHROUGH

약 3분으로 작업 과정을 설명하기.

  1. 게임의 질문과 역할 범위 · 약 25초

    이 게임의 선택은 지금 부화할지, 더 성장할 위험을 감수할지입니다. 팀이 만든 성장·굴리기·부화의 큰 흐름 안에서, 저는 속성 계통과 그 주변의 피드백·상호작용을 구체화했습니다. 화면을 보여줄 때도 게임 전체의 결과와 개인 수정 사례를 구분하겠습니다.

    근거 · 현재 포트폴리오의 플레이 흐름과 역할 표, 2026.09.03 개인 제작 이력.

  2. 획득과 결과를 잇는 설계 · 약 35초

    여정이 결과를 바꾼다는 설명만으로는 플레이어가 인과관계를 알기 어렵습니다. 그래서 획득한 속성이 장착 상태와 결과 이름으로 이어지게 하고, 바닥·HUD·알림에서 같은 색과 아이콘을 쓰도록 했습니다. 물리 효과가 있는 속성과 이름에만 반영되는 속성은 기록과 설명에서 구분했습니다. 이 부분은 기능의 존재보다 약속과 실제 동작의 일치가 중요했습니다.

    근거 · 속성 모듈 분리, HUD·토스트·개별 아이콘, 구현 상태 분류와 설명 정정 기록.

  3. 반응 없는 부화장의 원인 분해 · 약 45초

    부화장에 가까운데 입력이 안 되는 문제에서 처음 보이는 증상은 거리였습니다. 하지만 범위를 키워도 같았고, 진행 조건·입력 소비·판정 노드의 준비 시점이 별개 원인이었습니다. 입력이 도착하는 경로와 값이 적용되는 시점을 먼저 맞추고, 실제 범위와 같은 바닥 고리로 상태를 드러냈습니다. 이 사례에서 얻은 기준은 값이 적용되지 않을 때 크기보다 적용 시점과 소유 주체를 확인하자는 것입니다.

    근거 · 첫 부화 진행도 조건, UI 입력 처리, 판정 범위 초기화, 접근 고리·마젠타 변경 기록.

  4. 회복을 상태 복원으로 정의 · 약 40초

    부활 직후 다시 죽는 문제는 안전하지 않은 지점, 성장한 반지름, 남아 있는 낙하 속도가 겹친 사례였습니다. 지면·경사·위험을 확인하고, 현재 크기에 맞춰 복귀하며 물리 상태를 초기화하는 방향으로 다뤘습니다. 다만 보호를 많이 주는 것만으로 해결했다고 볼 수는 없습니다. 안전한 회복과 위험을 우회하는 악용 사이를 실제 플레이로 확인해야 합니다.

    근거 · 안전 지점·복귀 높이·물리 상태 초기화·부활 진단 기록.

  5. 협업과 확인 범위 · 약 35초

    AI 도구는 구현과 정리를 보조했지만, 바꿀 범위와 금지할 범위, 실제 동작과 완료 조건을 정하는 일은 작업자의 책임이었습니다. 당시 기록에는 엔진 실행과 병합이 남은 부분도 있습니다. 따라서 수정 기록, 현재 배포 반영, 처음 하는 사람의 이해도를 같은 성과로 묶지 않겠습니다. 다음에는 같은 짧은 동선으로 속성 이해·부화 발견·회복 후 조작을 관찰해 보완하려 합니다.

    근거 · 변경 금지 범위와 인수인계 기록, 당시 엔진·병합 검증 경계, 공개 페이지의 근거와 한계 표기.

03 / QUESTIONS & ANSWERS

판단의 이유를 묻는 질문.

Q1팀 게임인데 본인이 직접 책임진 범위는 어디까지인가요?

확인된 개인 작업은 속성 데이터·장착·효과·획득·조합과 작명 규칙, 관련 HUD와 부화장 UX, 부화·부활 동작 개선, 일부 소품 재질과 조명 이식입니다. 전체 콘셉트·월드·기본 게임 루프·타이틀과 도감 전체 화면·최종 병합과 배포는 팀 작업입니다. 저는 전체 기능을 혼자 만들었다고 설명하지 않고, 담당 계통에서 어떤 규칙을 정하고 어떤 문제를 수정했는지로 기여를 설명합니다. 기여율도 작업량 집계만으로 환산하지 않았습니다.

함께 제시할 근거

2026.09.03 개인 제작 이력의 직접 구현·구현 지휘 구분과 팀 작업 경계, 현재 포트폴리오 역할 표.

Q2속성 기능이 많다는 것보다 어떤 설계 판단을 강조할 수 있나요?

속성 개수보다 획득·표시·효과·결과가 연결되는지를 강조하겠습니다. 당시 일부 속성은 이름에는 반영되지만 물리 효과는 없었습니다. 그래서 목록에 있다는 이유로 모든 속성에 즉시 효과를 약속하지 않고, 동작 상태를 분류하고 실제와 다른 문구를 고쳤습니다. 순수한 무작위 부화는 비교 가능한 대안이지만, 실제로 비교 실험했다고 주장하지는 않겠습니다. 이 작업의 의도는 플레이어의 여정이 결과에 남는 관계를 드러내는 것이었고, 그 이해도는 추가 관찰이 필요합니다.

함께 제시할 근거

속성별 구현 상태 분류, 물리 효과와 작명 반영 구분, 실제 동작에 맞춘 설명 정정 기록.

Q3부화장 입력 문제에서 왜 판정 범위를 키우는 것으로 해결되지 않았나요?

거리와 입력 실행이 다른 문제였기 때문입니다. 기록상 진행도 조건이 첫 부화를 막았고, UI가 입력을 먼저 소비할 수 있었으며, 판정 노드 준비 전에 범위 설정이 호출돼 값이 반영되지 않았습니다. 그래서 조건·입력 전달·초기화 시점을 나눠 수정했습니다. 그다음 부화장 자신이 범위를 관리하고 실제 범위와 접근 고리를 일치시켰습니다. 먼저 증상을 재현한 뒤 값이 실제 대상에 적용되는지, 입력이 최종 동작까지 도달하는지 확인하는 접근입니다.

함께 제시할 근거

개인 제작 이력의 부화 진행 조건, 입력 경로, 판정 노드 생성 시점과 범위 소유 변경 기록.

Q4부활은 안전한 좌표 하나를 저장하면 되는 것 아닌가요?

성장하는 물리 오브젝트에서는 좌표만 안전하다고 볼 수 없습니다. 같은 위치도 계란 반지름이 커지면 지면에 끼거나 장애물과 겹칠 수 있고, 이동 전 속도가 남으면 다시 추락합니다. 당시에는 지면·경사·위험을 고려한 안전 지점과 현재 크기에 맞춘 복귀 높이, 물리 상태 초기화를 함께 다뤘습니다. 복귀 직후의 보호도 무제한으로 늘리지 않고 조작 회복과 위험 우회 가능성을 함께 봐야 합니다. 이 기준은 기록된 개선 방향이며, 모든 크기·지형 조합의 현재 배포 검증을 완료했다는 의미는 아닙니다.

함께 제시할 근거

안전 지점 판단, 계란 반지름·복귀 높이, 낙하 속도 잔존, 물리 이동 경로와 부활 진단 기록.

Q5AI가 구현을 도왔다면 본인의 판단과 검증은 무엇이었나요?

요구사항을 기능 이름으로만 주지 않고, 변경할 계통과 건드리지 않을 공용 영역, 실제 동작의 기준을 정하는 일이 제 책임이었습니다. 기록에는 공용 위험물의 재질·색을 바꾸지 않는 제한, 소품 재질의 재사용, 다수 오브젝트 처리 방식 같은 제약이 남아 있습니다. 생성된 결과도 화면의 색과 판정, 설명과 물리 효과가 일치하는지 확인해야 했습니다. 당시 제 환경에서 실행하지 못한 엔진 검사는 완료로 쓰지 않고 담당자에게 넘겼습니다. AI 보조와 사람의 설계·인수 책임을 구분해 설명하겠습니다.

함께 제시할 근거

개인 제작 이력의 수정 범위·금지 영역·재질 캐시·대량 오브젝트 제약과 엔진 검사 인수인계 기록.

Q6이 수정이 실제로 좋아졌다는 근거와 아직 부족한 근거는 무엇인가요?

현재 제시할 수 있는 것은 재현된 문제와 변경 이유, 당시 수정 이력과 보관 화면입니다. 오류가 줄었다는 사용자 수치나 행사 관람객의 이해도 향상은 측정 근거가 없어 주장하지 않겠습니다. 일부 기록은 당시 병합·엔진 확인 대기 상태였으므로 현재 버전에서의 확인도 별도로 필요합니다. 다음에는 동일한 짧은 과제로 속성 인지, 도움 없는 첫 부화, 회복 후 조작을 관찰하고 실패 원인을 나눠 기록하겠습니다. 기능이 있다는 근거와 사용자에게 효과가 있다는 근거를 구분하는 것이 제 기준입니다.

함께 제시할 근거

2026.09.03 기록의 병합·엔진 검사 상태, 현재 페이지의 보관 캡처 표기와 검증 경계.

04 / ROLE & EVIDENCE

내 역할과 확인한 범위를 구체화하기.

개인 기여는 2026.09.03 제작 이력 기준의 속성·장착·효과·조합·작명, 관련 HUD와 부화장 UX, 부화·부활 개선, 일부 소품 재질·조명 이식입니다. AI 보조 구현의 요구사항·제약·검토도 포함되지만 모든 코드를 직접 타이핑했다는 의미는 아닙니다. 전체 콘셉트·월드·기본 루프·전체 UI·통합·배포는 팀 작업이며 이후 후속 개발 전체를 개인 실적으로 합산하지 않습니다.

면접 전에 확인할 것

  • 면접 전 현재 플레이 버전과 보관 캡처의 차이를 직접 확인하고, 당시 수정 기록과 현재 동작을 구분해 말합니다.
  • 첫 부화와 반복 부화, 접근 방향·판정 경계·UI 열린 상태에서 안내와 실제 입력이 일치하는지 확인합니다.
  • 계란 크기와 지형을 바꿔 복귀 위치·속도·회복 기회 차감·즉시 재사망 여부를 확인합니다.
  • 속성마다 현재 효과·조건부 동작·작명 반영을 다시 확인해 설명 문구를 맞춥니다.
  • 정적 확인, 엔진 검사, 실제 화면 조작, 사용자 관찰은 각각 다른 근거로 기록합니다. 당시 미실행 검사를 완료한 것으로 말하지 않습니다.

다음 보강 자료

  • 처음 하는 사람의 획득 → HUD 확인 → 부화 결과 예측 과정을 관찰해 속성 설명과 교체 피드백을 다듬습니다.
  • 부화가 불가능한 경우 이유를 안내할지 검토합니다. 안내를 늘리는 것보다 입력 가능 조건을 이해하는지 먼저 확인합니다.
  • 부활 보호 시간과 안전 지점 갱신 기준은 공정한 회복과 위험 우회 가능성을 함께 보며 조정합니다.
  • 프로젝트가 계속 바뀌므로 사례마다 기준 날짜·반영 버전·확인 결과를 분리해 갱신합니다. 위 항목은 후속 검증 계획이며 이미 실험을 끝낸 성과가 아닙니다.
