문제 1

읽을 메일이 아니라, 실행할 업무를 찾는 문제

문제와 원인

메일을 읽고 내용을 이해했더라도 지금 누가 무엇을 언제 해야 하는지는 다시 판단해야 합니다. 요청과 회신, 변경된 결정, 이미 끝난 일이 한 대화에 섞이면 사용자는 여러 메일을 다시 열어 자신의 업무를 골라야 합니다. 이 프로젝트는 메일 수를 줄이는 기능보다 ‘대화에서 다음 행동을 확인하는 과정’을 문제로 정의했습니다.

메일 한 통의 요약은 해당 시점의 설명이 될 수 있지만 대화 전체의 최신 결정이나 담당을 대신하지 못합니다. 같은 제목의 정기 보고를 한 대화로 묶거나, 반대로 회신 이력을 놓치면 서로 다른 업무가 섞이거나 필요한 맥락이 빠질 수 있습니다.

선택한 해결과 이유

답장 헤더를 우선 사용해 대화를 연결하고, 헤더가 부족한 답장은 제한된 제목 조건으로 보완합니다. 대화의 내용은 할 일·담당·기한·결정사항으로 구조화하고, 오늘·프로젝트·일정에서 같은 업무를 서로 다른 관점으로 보여줍니다.

관리 단위를 메일에서 업무로 옮기면 ‘어떤 메일을 읽을까’와 ‘지금 무엇을 할까’를 연결할 수 있습니다. 오늘 화면은 실행 순서, 프로젝트는 진행과 결정의 맥락, 일정은 기한 확인을 담당하도록 나눴습니다.

감수한 점

대화 연결과 담당 판단이 틀리면 정리된 화면도 오해를 만들 수 있습니다. 그래서 요약을 자동 실행이나 자동 회신으로 연결하지 않고, 원래 대화의 맥락을 확인하며 사용자가 완료·제외·기한을 조정하는 범위에 둡니다.

확인한 근거

공개 데모의 오늘·답장 대기·프로젝트·일정 화면과 기존 대화 연결 코드에서 관리 단위와 표시 흐름을 확인할 수 있습니다. 공개 데모는 가상 메일을 사용하며 실제 메일함 연결과 AI 호출을 수행하지 않습니다.

다음 확인

담당·기한·요청 변경을 포함한 동일한 가상 대화 세트로 원본 메일만 보는 경우와 업무 화면을 보는 경우를 비교하고, 놓친 요청·잘못 고른 담당·원문 재확인 횟수를 기록하는 실험이 필요합니다. 시간 절감률은 이 비교 후에 제시할 수 있습니다.

문제 2

AI가 다시 정리해도, 사람의 판단을 잃지 않도록

문제와 원인

사용자가 이미 완료했거나 자신의 일이 아니라고 정리한 업무가 재분석 후 다시 나타나면 사용자는 같은 판단을 반복해야 합니다. 자동화가 일을 줄이는 대신 완료·제외 상태를 다시 확인하게 만드는 상황을 피하는 것이 두 번째 문제였습니다.

메일 내용에서 얻은 분석 결과와 사용자가 누른 상태를 같은 갱신 대상으로 취급하면 새 결과가 이전 판단을 덮어쓸 수 있습니다. ‘완료’, ‘남의 일’, ‘할 일 아님’, ‘기한을 직접 정함’은 서로 다른 의도인데 단일 숨김 상태로 합치면 복구와 후속 요청 처리의 기준도 불명확해집니다.

선택한 해결과 이유

메일·분석 자료와 별도로 사용자 피드백을 보관하고, 완료·제외·업무삭제와 복구를 구분합니다. 직접 정한 기한은 추출된 기한보다 우선합니다. ‘남의 일’·‘할 일 아님’으로 제외한 대화는 분석 제외 규칙에 연결하고, 제외 이후 사용자가 받는사람으로 다시 지목된 새 요청은 별도 알림으로 드러냅니다.

분석 결과는 바뀔 수 있지만 사용자가 왜 제외하고 무엇을 직접 수정했는지는 별도로 유지할 가치가 있습니다. 현재 상태와 변경 기록을 나누면 사용자가 판단을 되돌리거나 새 요청의 맥락을 확인할 수 있습니다.

감수한 점

모든 새 요청을 자동으로 복구하면 예전 제외 의도가 무시되고, 반대로 계속 숨기면 중요한 요청을 놓칠 수 있습니다. 현재 설계는 제외 상태와 후속 지목 사실을 구분하지만, 재분석 과정에서 업무 문구·식별자가 달라지는 경우의 연결은 계속 검증해야 합니다.

확인한 근거

공개 데모의 완료·제외·내 일 아님·복구·직접 기한 변경과 피드백의 별도 저장 구조를 확인할 수 있습니다. 이 동작의 존재가 모든 재분석 사례에서 사용자 상태 보존이 완전하다는 증명은 아닙니다.

다음 확인

업무 문구 수정, 한 업무의 분할·합침, 제외 뒤 새 요청 수신, 직접 기한 설정 후 재분석을 각각 시나리오로 만들고 상태가 사라지거나 잘못 연결되는지 확인할 필요가 있습니다. 면접에서는 이 예외를 남은 운영 검증으로 구분해 설명할 수 있습니다.

문제 3

명확한 규칙과 내용 이해를 나누어 반복 처리를 줄이기

문제와 원인

모든 메일을 매번 같은 방식으로 AI에 보내면 이미 읽은 인용문과 바뀌지 않은 대화를 반복 처리하게 됩니다. 프로젝트 분류 규칙 하나를 수정할 때마다 내용 분석까지 다시 실행하는 것도 불필요한 연결입니다.

어느 프로젝트에 속하는지 판단하는 조건과 대화에서 할 일을 이해하는 작업을 하나로 묶으면, 작은 운영 변경이 전체 재분석으로 이어질 수 있습니다. 입력을 줄였다는 사실만으로는 업무 품질이 유지됐는지도 알 수 없습니다.

선택한 해결과 이유

제목 키워드·태그·발신 도메인을 사용하는 프로젝트 분류는 규칙으로 처리하고, 대화의 업무 구조화는 AI의 역할로 분리합니다. 변경된 대화 중심으로 분석하고 인용된 중복 내용을 줄이며, 호출·토큰·지연·실패 기록을 사용 현황에서 확인하도록 구성했습니다.

규칙으로 설명 가능한 판단은 설정을 바꿔 다시 적용할 수 있고, AI는 문맥 이해가 필요한 부분에 사용할 수 있습니다. 사용량을 기록하면 줄어든 입력과 늘어난 재확인 부담을 함께 살필 출발점이 생깁니다.

감수한 점

규칙은 알려진 분류 조건을 명확히 관리하는 대신 새로운 고객사나 예외에 맞춘 유지보수가 필요합니다. 증분 분석은 중복 입력을 줄일 수 있지만 오래된 맥락이나 번복된 결정을 놓칠 수 있어 전체 맥락 재확인 기준이 필요합니다. 절감된 토큰을 곧바로 절약된 업무시간으로 해석하지 않습니다.

확인한 근거

기존 분류 규칙 페이지, 토큰 사용 현황, 변경된 대화 중심의 분석 코드와 공개 데모 구성을 근거로 설명할 수 있습니다. 공개 데모의 사용량 기록은 미리 준비한 가상 기록이며 실시간 운영 성과가 아닙니다.

다음 확인

같은 대화 세트에 전체 분석과 증분 분석을 적용해 누락·담당 오판·수동 정정 비율을 먼저 비교하고, 이후 입력량·호출 시간·실패율을 함께 봐야 합니다. 업무 효과를 주장하려면 별도의 실제 사용 비교가 필요합니다.

프로젝트의 동작·설계 근거와 실제 사용 효과는 구분해 설명합니다.

03 / KEY DECISIONS

AI가 정리하고,
최종 판단은 사용자에게 남깁니다.

분류·구조화·완료 처리의 책임을 나누어 동작 규칙을 정리했습니다.

01

메일이 아닌 업무를 관리 단위로

대화에서 해야 할 행동과 담당·기한을 구조화하고, 같은 업무를 오늘·프로젝트·일정 화면에 연결했습니다.

사용자 경험메일을 다시 찾는 과정과 지금 할 일을 확인하는 과정을 연결합니다.
02

AI 결과와 사용자 상태 분리

완료·제외·내 일 아님·복구를 구분하고, 직접 정한 기한을 우선 적용합니다. 새 분석이 이전의 판단을 임의로 초기화하지 않도록 구성했습니다.

설계 기준자동화가 사용자의 판단을 덮어쓰지 않도록 상태를 보존합니다.
03

분류는 규칙, 내용 정리는 AI

프로젝트 분류는 제목·태그·도메인 규칙으로, 대화의 업무 정리는 AI로 처리합니다. 규칙 변경만으로 재분류할 수 있는 영역을 나눴습니다.

운영 기준내용 이해가 필요한 작업과 명확한 조건으로 처리할 작업을 분리합니다.
04

반복 처리와 실패를 기록

변경된 대화 중심으로 재처리하고 호출·토큰·실패 기록을 관리합니다. 사용량의 확인과 실제 업무 효과 측정을 구분했습니다.

검증 기준입력 크기·토큰 기록을 곧바로 업무시간 절감률로 해석하지 않습니다.
04 / INTERFACE

오늘의 실행과
프로젝트의 맥락을 함께.

공개 샘플에 포함된 실제 화면입니다. 사람·회사·메일과 업무 내용은 가상으로 구성되어 있습니다.

직접 볼 수 있는 공개 데모완료·제외·기한·색상 등 데모의 변경 사항은 방문자 브라우저에 저장됩니다. 실제 메일함에 접속하거나 AI를 호출하지 않습니다.
05 / SCOPE & LEARNING

동작하는 샘플과
실제 효과 검증을 구분합니다.

공개 데모와 기존 프로젝트 설명 자료를 바탕으로 정리했습니다. 실제 메일과 운영 데이터를 공개하지 않습니다.
