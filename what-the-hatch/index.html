영역개인 담당팀 작업과의 경계

이름과 결과 서사조합 등급과 작명 규칙을 만들고 획득한 속성이 결과 이름에 남도록 설계.전체 세계관과 월드 진행, 부화 생명체의 공용 파츠 체계는 팀의 상위 기획.
HUD와 부화장 UX속성 슬롯·획득 알림·개별 색·3D 아이콘, 부화장 접근 고리와 피드백을 구성.타이틀·부화·도감의 전체 화면은 팀의 UI 제작 범위.
실패와 회복부화 입력·판정 초기화 문제를 분리해 수정. 안전 지점·성장 크기·물리 상태를 고려한 부활 흐름 개선.전체 물리·맵·위험물 설계를 개인 단독 작업으로 표현하지 않음.
시각 품질과 문서소품 재질 보완, 랩에서 만든 환경·조명 이식, 속성별 구현 상태와 실제 동작을 문서화.월드 제작·전체 병합·최종 웹 배포는 팀 내 다른 담당의 작업.

기여 근거: 기존 개인 제작 이력과 속성·부화장·부활 관련 변경 기록. 역할은 확인된 작업 내용으로 표기하며 기여율이나 전체 제작 성과로 환산하지 않았습니다.

문제 1

여정이 결과를 바꾼다는 규칙을 눈에 보이는 선택으로

문제와 원인

계란을 굴려 생명체를 부화시킨다는 콘셉트만으로는, 방금 획득한 대상이 내 상태와 부화 결과를 어떻게 바꾸는지 알기 어렵습니다. 속성 이름이 화면에 나타나는 것과 플레이 중 실제 효과가 생기는 것도 구분해야 했습니다.

획득물·장착 상태·물리 효과·결과 작명이 서로 다른 단계에 존재했습니다. 일부 속성은 당시 물리 효과가 아직 없었고, 설명이 실제 동작보다 앞서면 플레이어에게 잘못된 기대를 줄 수 있었습니다.

선택한 해결과 이유

개인 담당 범위에서 속성 데이터, 장착 상태, 효과, 획득, 조합과 작명 규칙을 나누어 연결했습니다. 바닥의 획득물·HUD 슬롯·획득 알림에는 같은 속성의 색과 아이콘을 사용했습니다. 효과 구현·조건부 동작·후속 구현·이름 반영 범위를 따로 기록하고, 실제 동작과 다른 설명은 고쳤습니다.

플레이어가 획득 → 현재 상태 → 결과의 관계를 따라갈 수 있어야 여정에 따른 변화가 선택으로 느껴집니다. 기능 목록을 늘리는 것보다, 화면의 약속과 실제 동작을 일치시키는 일을 우선했습니다.

감수한 점

속성 조합은 결과의 다양성을 만들지만 장착과 교체 규칙의 설명 부담도 늘립니다. 이름에만 반영되는 속성을 즉시 효과가 있는 속성과 똑같이 안내하면 혼란이 생길 수 있어, 구현 상태와 설명을 계속 함께 관리해야 합니다.

확인한 근거

2026.09.03 개인 제작 이력의 속성·장착·효과·조합·작명 분리 기록, 속성별 구현 상태 정리, 아이콘·색·HUD 개선 기록에 근거합니다. 당시의 구현 범위를 현재 전체 버전의 완성도나 사용성 성과로 환산하지 않았습니다.

다음 확인

처음 플레이하는 사람이 획득한 속성을 HUD에서 다시 찾고, 현재 적용되는 효과와 부화 이름에 반영되는 요소를 구분할 수 있는지 관찰합니다. 이해가 멈추는 지점을 기록한 뒤 설명과 피드백을 다듬을 계획입니다.

문제 2

부화장 앞에서 눌러도 반응이 없는 이유를 나누어 해결

문제와 원인

부화장에 접근했다는 안내가 나와도 입력 후 아무 일도 일어나지 않는 문제가 있었습니다. 판정 범위를 넓히는 수정만으로는 해결되지 않아, 화면의 안내와 실제 동작에 대한 신뢰가 깨질 수 있었습니다.

당시 기록에는 세 원인이 구분되어 있습니다. 진행도 조건이 첫 부화를 막았고, 다른 UI가 입력을 먼저 처리할 수 있었으며, 판정 노드가 준비되기 전에 범위를 설정해 값이 실제로 적용되지 않았습니다.

선택한 해결과 이유

불필요한 진행도 조건과 입력 경로를 정리하고, 부화장이 자신의 판정 범위를 관리하도록 수정했습니다. 옆에서 접근하는 경우를 고려해 판정 형태를 바꾸고, 실제 판정과 같은 범위의 바닥 고리로 접근 가능 상태를 보여줬습니다. 위험물의 주황·붉은 계열과 혼동되지 않도록 부화장에는 마젠타를 사용했습니다.

상호작용은 가까워 보이는 것, 판정 범위 안에 들어오는 것, 입력이 실행되는 것이 모두 연결되어야 성립합니다. 숫자를 키우기 전에 조건·입력·초기화 시점을 나눠 확인한 것이 해결의 핵심이었습니다.

감수한 점

접근 범위와 시각 신호를 강화하면 발견은 쉬워지지만, 의도하지 않은 부화나 주변 장애물의 가림이 생길 수 있습니다. 넓은 범위 자체를 성공으로 보지 않고 경계에서의 예측 가능성을 함께 확인해야 합니다.

확인한 근거

2026.09.03 개인 제작 이력의 부화 입력, 진행도 조건, 판정 노드 초기화 시점, 원통형 범위와 접근 고리, 색상 변경 기록을 근거로 설명합니다. 완료율 향상이나 실제 관람객의 오류 감소 수치는 확인되지 않았습니다.

다음 확인

정면·측면·경계에서 접근하고, UI를 열거나 닫은 상태와 첫 부화·반복 부화를 나눠 확인합니다. 안내가 켜지는 위치와 실제 입력이 가능한 위치가 같은지 살피고, 부화 후 상태 초기화까지 한 흐름으로 검증합니다.

문제 3

부활을 좌표 이동이 아닌 플레이 가능한 상태의 복원으로

문제와 원인

되살아난 직후 다시 추락하거나 바닥에 끼는 문제가 있었습니다. 성장한 계란의 크기나 낙하 속도가 제대로 반영되지 않으면 회복 기회가 연속으로 소모되어, 실패를 복구하는 기능이 추가 실패를 만들었습니다.

지면에 닿았다는 사실만으로는 안전한 복귀 지점이라고 판단하기 어려웠습니다. 고정된 복귀 높이는 성장한 계란의 크기와 맞지 않았고, 좌표만 바꾸면 물리 엔진의 속도와 이동 상태가 남을 수 있었습니다.

선택한 해결과 이유

당시 수정은 일부 변경이 병합·엔진 검증 대기인 상태였습니다. 안전 지점 판단에 지면 확인·경사·위험 구역을 함께 고려하고, 지면과 현재 계란 크기를 기준으로 복귀 위치를 계산하는 방향으로 개선했습니다. 물리 이동과 순간 이동 경로를 정리해 복귀 시 물리 상태를 초기화하고, 회복 직후의 보호와 피드백도 함께 다뤘습니다.

플레이어가 기대하는 부활의 결과는 이전 좌표에 존재하는 것이 아니라 다시 조작할 수 있는 상태입니다. 위치·크기·속도·안전성을 함께 다뤄야 같은 실패가 즉시 반복되는 구조를 줄일 수 있습니다.

감수한 점

안전 판정을 지나치게 엄격하게 잡으면 복귀 거리가 길어지고, 보호 시간을 과하게 주면 위험을 회피하는 수단이 될 수 있습니다. 회복의 공정함과 원래 게임의 긴장감을 함께 조정해야 합니다.

확인한 근거

2026.09.03 개인 제작 이력의 안전 지점, 계란 반지름과 복귀 높이, 낙하 속도, 물리 상태 초기화 및 부활 진단 기록에 근거합니다. 당시 일부 변경은 병합·엔진 검증 대기 상태였으므로, 이 기록을 현재 배포판 전체에서의 재검증 결과로 표현하지 않았습니다.

다음 확인

작은 계란과 크게 성장한 계란으로 평지·경사·절벽·위험 구역에서 회복을 반복합니다. 회복 기회가 한 번만 차감되는지, 복귀 직후 조작이 가능한지, 재시작 후에도 같은 안전 기준이 적용되는지 실제 플레이로 확인합니다.

프로젝트의 동작·설계 근거와 실제 사용 효과는 구분해 설명합니다.

03 / DESIGN DECISIONS

보이지 않던 규칙을,
보고 선택할 수 있게.

핵심은 기능을 많이 더하는 일이 아니라, 플레이어가 획득과 위험·결과를 같은 흐름으로 이해하게 만드는 일이었습니다.

01

여정의 영향을 손으로 고르게

바닥에서 속성을 획득하고 장착 상태로 이어지게 했습니다. 제작 이력 기준 42종의 속성과 3칸 장착을 정의하고, 데이터·효과·조합·상태를 별도 모듈로 나눴습니다.

설계 의도“플레이 기록이 결과를 바꾼다”는 추상적인 설명을 획득과 선택이라는 구체적인 행동으로 옮겼습니다.
02

같은 속성은 같은 색과 아이콘으로

바닥의 속성을 글자만으로 표시하지 않고 개별 아이콘과 색으로 구분했습니다. HUD 슬롯과 획득 알림도 같은 표현을 사용해 시선이 이동해도 대상을 이어서 읽게 했습니다.

사용자 경험분류색 하나로 뭉개지던 개별 속성의 차이를 보여주고, 수집한 대상과 화면의 상태를 연결했습니다.
03

부화장의 판정 범위를 화면에

상호작용 범위와 같은 크기의 고리를 바닥에 표시하고, 진입하면 밝기와 움직임이 바뀌게 했습니다. 위험물과 혼동되던 색도 부화장 고유의 마젠타로 구분했습니다.

설계 기준“가까이 가면 된다”는 안내만 두지 않고, 어느 범위에서 어떤 행동이 가능한지 화면으로 설명했습니다.
04

모든 속성에 즉시 효과를 약속하지 않기

당시 속성을 물리 효과 구현·조건부·후속 구현·이름 반영 범위로 나누어 기록했습니다. 즉시 효과가 없는 속성도 결과 작명에는 반영하되, 설명과 실제 동작이 다른 문구는 정정했습니다.

운영과 문서목록에 있다는 사실과 플레이 중 작동한다는 사실을 구분했습니다. 이 분류는 당시 제작 기록이며 현재 전체 버전의 완성도 수치가 아닙니다.
04 / ACTUAL SCREENS

타이틀에서 여정과 부화장까지,
실제 화면으로 확인합니다.

프로젝트에 보관된 게임 캡처입니다. 모든 이미지를 처음부터 펼쳐 두었고, 이미지를 선택하면 확대할 수 있습니다.

이 캡처는 프로젝트의 보관 자료입니다. 이후 개발 중인 화면·규칙과 차이가 있을 수 있으며, 실제 플레이 링크의 버전과 제작 당시 개인 작업 기록을 구분해 보실 수 있습니다.

05 / PROBLEM SOLVING

수치를 바꾸기 전에,
동작이 연결되는 지점을 확인했습니다.

마감 이후에는 부화·회복·가시성처럼 플레이 흐름을 끊는 문제를 우선 정리했습니다. 아래는 당시 변경 기록에 남아 있는 개인 작업 사례입니다.

부화 입력 · 판정 · 초기화

부화장 앞에서 입력해도 아무 일도 일어나지 않았다.

문제 — 접근 안내는 나오지만 부화 입력이 처리되지 않았습니다. 판정 범위를 키워도 결과가 같아, 숫자만의 문제로 보기 어려웠습니다.

확인 — 진행도 조건이 첫 부화를 막고 있었고, 입력이 다른 UI에서 먼저 처리될 수 있었습니다. 범위 설정도 판정 노드가 생성되기 전에 호출돼 실제로 반영되지 않았습니다.

수정 — 불필요한 진행도 조건과 입력 경로를 정리하고, 부화장 자체가 판정 범위를 소유하도록 바꿨습니다. 판정 형태와 바닥 고리의 범위를 일치시켜, 설정과 표시가 같은 기준을 쓰게 했습니다.

남긴 기준 — 값이 적용되지 않을 때는 값의 크기뿐 아니라 적용 시점과 대상의 생명주기를 확인합니다.

부활 · 안전 지점 · 물리 상태

되살아나자마자 다시 죽는 부활을 고쳤다.

문제 — 낭떠러지 근처에서 부활하거나, 커진 계란이 바닥에 끼거나, 낙하 속도를 유지한 채 이동하면서 회복 기회가 연쇄 소모됐습니다.

확인 — 단순 접촉 횟수가 안전을 뜻하지 않았고, 고정 높이는 성장하는 물체에 맞지 않았습니다. 일반 좌표 변경과 물리 엔진의 상태 변경도 서로 다른 경로였습니다.

수정 — 실제 발밑 지형과 기울기·위험 여부를 확인해 안전 지점을 저장했습니다. 바닥면과 현재 크기로 복원 위치를 계산하고, 공통 물리 이동 경로와 부활 직후 유예·알림을 연결했습니다.

남긴 기준 — ‘안전’이라는 이름을 믿기보다 안전을 판정하는 조건을 확인하고, 같은 행동을 수행하는 경로를 하나로 모읍니다.

소품 재질 · 파일 소유권 · 이식

다른 담당의 파일을 덮어쓰지 않고 시각 품질을 개선했다.

문제 — 금속이나 표시 장치의 재질감이 약했지만, 해당 소품을 배치하는 파일은 다른 담당의 작업 영역이었습니다.

수정 — 소품의 의미에 따라 재질을 보완하는 별도 모듈을 만들고, 기존에 정한 색과 배치를 유지했습니다. 독립 랩에 완성된 환경·조명도 필요한 범위만 본 게임으로 이식했습니다.

남긴 기준 — 보완할 표현과 이미 합의된 기획 값을 구분합니다. 검증 환경이 없을 때는 미검증 사실과 확인할 항목을 병합 담당에게 명시적으로 인계했습니다.

06 / COLLABORATION

사람과 AI가 함께 작업해도,
수정 범위와 책임은 분명하게.

짧은 일정에서 개인 담당의 계통을 완성하고, 팀의 게임 루프에 연결하는 방식으로 진행했습니다. 전체 일정과 최종 병합·배포는 팀 오너가 관리했습니다.

새 기능은 독립 모듈로

속성 데이터·상태·효과·조합·획득을 신규 파일로 나누어, 다른 사람이 작업 중인 공통 파일을 동시에 크게 바꾸지 않도록 했습니다. 공통 연결부는 필요한 범위만 조정했습니다.

랩에서 확인하고 필요한 부분을 이식

독립 실험 환경에서 실루엣과 표현을 확인하고, 본 게임에는 완성된 기능을 옮겼습니다. 다른 팀원이 만든 월드 환경을 가져오는 경우에는 원래 제작 범위와 이식 작업을 구분했습니다.

AI를 구현·조사의 보조로

기능 구조화, 구현과 버그 원인 분리에 AI 코딩 도구를 활용했습니다. 정한 규칙을 임의로 바꾸기보다 작업 범위와 결과를 검토하고, 사람이 확정한 기획과 맞추는 데 사용했습니다.

검사를 사용 경험으로 오해하지 않기

코드가 실행된다는 검사만으로 부화와 안전한 부활을 증명할 수 없었습니다. 입력·판정·물리 상태가 실제로 연결되는지 확인하는 기준을 문제별로 구체화했습니다.

담당과 완료의 구분개인 제작 이력은 속성·작명·부화장 UX·문제 해결을 중심으로 정리했습니다. 전체 기획 확정, 월드 제작, 공용 UI, 통합·배포를 개인 단독 제작으로 포함하지 않았습니다.
07 / EVIDENCE & SCOPE

제작 기록과 실제 효과를
서로 다른 근거로 남깁니다.

기존 제작 이력의 사실을 공개 사례로 다시 정리했습니다. 코드 양이나 커밋 수를 제품의 재미·품질·개인 기여율로 해석하지 않습니다.

기록으로 확인한 범위

무엇을 만들고 바꿨는가

  • 2026.08.31 행사 제출 이후 2026.09.03까지 정리된 개인 제작 기록.
  • 속성 데이터·장착·효과·획득·조합 및 작명 체계의 구현.
  • 부화장 접근 표시와 입력·판정 초기화 문제의 수정 기록.
  • 안전 지점·물리 상태를 고려한 부활과 시각 피드백 개선.
  • 팀과 개인의 담당 구분, 독립 모듈·랩·검증 인계 방식.
  • 프로젝트 보관 캡처와 공개 게임 링크.

문서만으로 주장하지 않는 것

08 / TAKEAWAYS

기능을 만드는 것에서,
플레이어가 믿는 동작으로.

이 프로젝트에서 배운 것은 규칙을 더하는 속도만이 아니라, 화면이 약속한 행동과 실제 판정이 일치해야 한다는 점입니다.

추상적인 의도를 행동 단위로

여정에 의미를 주겠다는 콘셉트를 속성 획득·장착·작명으로 구체화했습니다. 플레이어가 직접 고르는 행동과 결과 사이에 연결을 만드는 경험이었습니다.

보이지 않는 상태를 설명하기

상호작용 범위와 부활 상태처럼 보이지 않던 규칙을 화면 피드백과 문서로 드러냈습니다. 다음 검증에서는 처음 플레이하는 사람이 도움 없이 부화하고 다시 시도하는 과정을 확인할 수 있습니다.

다음 확인 질문처음 플레이하는 사람이 획득한 속성, 부화할 수 있는 범위, 실패 후 남은 기회를 화면만 보고 이해할 수 있는가? 같은 짧은 동선으로 관찰하고 개선할 항목입니다.
